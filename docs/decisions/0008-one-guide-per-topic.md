# 0008. 手法类文档：一个主题只许一份，新做法覆盖旧做法

## 背景

用户提出的是这轮治理里最深的一层问题：

> 「任何的想法只是当前所认为的最优解。新增路线的规范，后面发现不是最优解，还要改文档。
> 更重要的是一种情况：我提了个新想法，或者他发现了一个新做法，要能**及时地把旧文档覆盖**。
> 这样下次新来的 agent 提这件事时，自动就能找到最新文档，不需要再问我，
> 也不用沿用旧方法再踩同一个坑。」

这类失效的性质和前面两种都不同：

| 失效类型 | 触发信号 | 能不能自动发现 |
|---|---|---|
| 结构化事实过期（路线数、放行名单） | 代码变了 | 能（STATUS 重新生成即红） |
| 语义漂移（架构描述与实现不符） | 代码变了 | 半能（提交时按本次改动即时判定该复审哪几份 + 必须留 `Doc-reviewed:`） |
| **判断过时（当初认为对的做法不再是最优）** | **代码可以一点没变** | **不能** |

第三种还有一个更糟的后果：**并存**。agent 遇到更好的做法时，最省力的动作是
「再写一份新的」，于是 `live_verification.md` 与 `live_verification_v2.md` 同时在库，
下一个 agent 极可能挑到旧的那份 —— 于是旧坑被踩第二遍，而文档看起来"都有"。

## 决定

新增一个文档通道 **`docs/howto/`（手法）**，并给它三条硬约束，全部机器可查：

1. **一个主题只许一份文件**。frontmatter 必须有 `topic: <英文短键>`，全库唯一。
   门禁发现重复直接红，报错写明「改旧的那份，不要新开」。
2. **必须有「更改记录」小节**：日期 / 改了什么 / 依据。覆盖要留痕，历史不丢。
3. **必须带 `last_verified` 与 `review_when`**。后者写「什么变了就该重读我」，
   比「请定期复核」有用 —— 前者会被忽略，后者能触发。
4. **旧做法不删，留一行墓碑**：`已作废（日期）：原做法 X，因为 Y，现在看 Z`。
   搜旧词的人（包括记着旧做法的 agent）会被引导到新做法，而不是搜不到就自己再试一遍。

配套：`docs/README.md` 的「按你要做的事找」里，同一个主题**只有一个入口**。
入口唯一，是"不许并存"的另一半 —— 索引里出现两个入口，等于允许两份文档。

## 后果

- 想到更好的做法时，正确动作变成「改那一份 + 加一行更改记录」，而不是「再写一份」。
  这份摩擦是**故意保留**的，它挡掉的正是"文档越写越多、每份都半对"。
- `review_when` 需要人写、也可能写错。但它比没有强：至少下一个人知道
  「改 `core/elevation.py` 时要回头看这份手册」。
- 墓碑会让文件变长一点。值得：它保住了"为什么放弃旧做法"这条信息，
  否则半年后有人会把旧做法当新发现重新提出来。

## 考虑过但被否掉的方案

| 方案 | 为什么没选 |
|---|---|
| 用 ADR 的 `superseded` 代替 | ADR 保留**历史版本**，用户要的是**只留最新一份**。ADR 适合「决策」，手法需要「唯一现行版」 |
| 靠"请及时更新文档"的约定 | 试过了，就是这轮治理的起因 |
| 给文档加有效期，过期就强制重写 | 日期新不代表内容对，而且会逼出"只改日期不改内容"的敷衍 |
| 发现同主题就自动合并 | 合并需要判断力，机器做不了；能做的只是**拦住并存**并让人选一份 |

## 现行状态补记（2026-11-09）

上表「语义漂移」那一格的「复审游标提醒」是写这份决策时的机制，**已作废**：
2026-11-09 起 `tools/doc_review.py` 改为按本次暂存区 / 工作区改动即时判定该复审哪几份，
不再有 `doc-review-cursor.txt`；提交信息必须带一行 `Doc-reviewed:`（`tools/githooks/commit-msg` 会拦）。
本决策的其余结论（一个主题一份、改旧的不另开、留墓碑、带 `last_verified` / `review_when`）**不变**。
