# 0006. PC 滑动必须抢前台，抓帧不怕遮挡，最小化要自动还原

## 背景

2026-11-08 每日任务连打，三条路线同时出问题，根因最后收敛到「PC 窗口 I/O」这一层：

- **刷书签报错退出**：`滚动到底部结果不明确 … 峰值画面差=25.811`，
  滑了两次、每次干等 20 秒，刷新 0 次。
- **骑士团捐赠漏捐**：日志写「已经没有可支援的成员了」，用户看到的是「别人要什么我并没有给」。
- 用户提出疑问：「之前都能滚动，是不是新增 PC 后台运行导致的？」「后台点击能做，拖动为什么不能？」
  「完全盖住或最小化就抓不到？那后台运行就没意义了。」

查证到的三个事实：

1. 同一天 13:31 前台 `SendInput` 拖拽**连续 5 次滚动成功**（画面差 30~33，刷书签跑到 96/100）；
   21:08 后台 `PostMessage` 拖拽消息全发出去了、**列表一个像素没动** ——
   诊断图里两张截图的商品行完全相同，「画面差 25.811」全部来自商人对话气泡的弹出与消失。
   骑士团那一步是同一个病：滑了一下没滚动，程序以为下面没人了。
2. 客户端导入表里有 `RegisterRawInputDevices` / `GetRawInputData` —— 鼠标走 **Raw Input**，
   而 Raw Input 只喂前台窗口。所以后台拖拽、后台滚轮**都**过不去，不是实现没写对。
3. 遮挡不影响抓帧：把游戏整个用纯色窗口盖住，`BitBlt` 仍返回完整大厅画面
   （`std` 62.2，未遮挡 63.7）。`core/pc_window.py` 里 2026-08-30 的结论也是这条。
   真正取不到画面的只有**最小化**：客户区变 0×0，那份画布被系统收走。

## 决定

1. **`swipe()` 不再按输入通道分支**：`background` 下也先 `activate()` 再 `SendInput` 拖拽。
   点击不受影响，仍可留在后台。同时删掉 `_background_swipe()`（已证实无效，留着会被误用）。
2. **滑完立刻把前台还回去**（`_restore_foreground`）。点击不还原（2026-11-01 用户拍板，
   避免窗口来回闪），但滑动一轮要重复几百次，不还原等于整轮占着屏幕；
   还原后每次占用前台的时长 ≈ 滑动本身（0.5 秒 + 一次切换）。
3. **最小化自动还原**写进 `_validated_rect()`：任何抓帧/输入之前先看 `IsIconic`，
   先 `SW_SHOWNOACTIVATE`（不抢焦点），不生效才 `SW_RESTORE` —— 与 `core/window.py` 同口径。
4. **不再把「被遮挡」当风险**：文档与用户须知里关于「别被挡住」的措辞撤掉，
   只留「别最小化」，而且最小化现在也会被自动还原。

明确不做：不为后台拖拽再写第二套实现，也不去试 `SendInput` 注入到非前台窗口 ——
Raw Input 的限制在客户端那一侧，不是我们能绕的。

## 调研过哪些现成方案（2026-11-08 23:00，用户要求「别自己造轮子」）

| 来源 | 它的做法 | 能不能搬到 epic7 |
|---|---|---|
| **参考项目 zzz-od** `pc_controller_base.py::_background_drag` | `ClientToScreen + SetCursorPos` 驱动，`PostMessage(WM_LBUTTONDOWN/UP)` 的 **lParam 传 0**，拖动过程**不发** `WM_MOUSEMOVE` | 照抄这两处差异后实测：商品栏差 **0.319**，列表没动。差别在客户端 —— 绝区零的 UI 读真实光标，epic7 走 Raw Input |
| **参考项目** `win_scroll()` | `pyautogui.scroll` —— 本身就是**前台** | 说明参考项目的后台能力也只有「点击 + 拖拽」，没有可借的后台滚动方案 |
| **参考项目** `_gamepad_click()` | 虚拟手柄按键替代点击（`xbox_lb` + `xbox_a`） | 绝区零支持手柄；epic7 是否支持未确认，且「手柄摇杆滚列表」还要游戏自己实现过 |
| **竞品 APK**（`其他成熟的产品/`） | 安卓端：native 截屏 + 无障碍服务点击 | 与 PC 外控是两条路，不适用 |

结论：本地能查的三条现成路线都试过或明确不适用，**前台是最后手段**，但做了「滑完还原」把干扰压到最短。

## 后果

- **接受了的缺点**：走含滑动的路线（刷书签 / 骑士团 / 迷宫 / 幸存者）时，
  每次滑动会把游戏窗口切到前面，滑完立刻还原原窗口 —— 闪一下，大约 0.5~1 秒。
  刷书签一轮滑 2 次、300 轮就是 600 次，这个跳变会反复出现。
  用户明确要求「前台是最后的方法」，同时强调切前台一两秒「很严重、很影响使用」——
  所以这是**仍待消除的缺点**，不是被接受下来的代价。一旦客户端换掉 Raw Input、
  或找到可后台滚动的成熟方案，应优先换掉这条（调研结论见上表）。
- **收益**：纯点击类路线完全后台（不抢焦点、不占鼠标、被完全遮挡也能跑）；
  含滑动的路线从「必然失败」回到可用。
- 真机验证（2026-11-08 23:18，`background` 通道）：
  - 反向拖（回顶部）：商品栏差 **15.619**；
  - 正向拖（到底部）：**15.577**；
  - 每次日志都带 `前台已还原=是`。
  此前一次「0.445 没动」是**假失败** —— 当时列表已经在底部，正向拖本来就不动。
- 曾经的猜测「后台通道能覆盖所有动作」被证伪，`PC_TEMPLATE_MIGRATION.md`
中那条「后台 `PostMessage` 点击实测无效」也一并更正（现为「后台点击实测有效」，
见该文档 §2.2 附近）。

## 考虑过但被否掉的方案

- **后台滚轮 `WM_MOUSEWHEEL`**：理论上最优（纯消息、不动光标、不抢前台），
  但滚轮同样走 Raw Input，后台收不到。没做真机验证是因为提权需要 UAC 确认，
  而结论已经被同一份导入表证据覆盖 —— 若将来客户端换了输入模型，可以再试。
- **`SendInput` 直接打到后台窗口**：按键事件由系统按前台窗口路由，做不到。
- **靠 `PrintWindow` 绕开**：OpenGL 客户端返回黑图，早已否决（见 §1.1）。

> **现行补记（2026-11-09）**：上面「后台滚轮」那条写「没做真机验证是因为提权需要 UAC 确认」，
> 是当时的理由；现行 [实机闭环验证](../howto/live_verification.md) 已查明该机
> `ConsentPromptBehaviorAdmin=0`（静默提权，从不弹 UAC），那句提示从未兑现。
> 本决策的结论（**PC 滑动必须抢前台**、拖拽 / Raw Input 无后台方案）**不变**。
