# 0011. 按玩家行为的影响范围分层验收变更

## 背景

最近 50 个主线提交按原 PR 选择器回放，48 个需要完整回归。主线补星的越界选卡与开局接力曾同在一个路线文件内；前者只决定卡片位置，后者决定可以从哪些游戏状态接管。两者影响不同。一个文件名不足以说明玩家会遇到哪些变化。

## 决定

以玩家可观察的行为和使用该行为的入口确定验收范围。

- 开发时先复现故障及相邻反例。可独立维护的逻辑须有明确输入、输出和已核对的调用方，才能登记为可定向合并的行为。保持普通路线的开发方式，只在实际维护值得时拆出边界。
- 合并时，本地与 CI 从同一函数读取该行为所需的路线回放、正常入口、接力和安全契约测试。多个改动取并集；出现未登记的运行代码、共享导航或输入、资源提交、生产模板或未知路径时，PR 执行完整离线回归。全仓编译、静态和治理检查继续执行。
- 第一个试点是主线补星篇章卡片的候选和画布落点。给定画面和已检查的星标，只返回候选；滚动、点击、开战和恢复仍由路线处理。新增依赖或运行时调用方会触发边界测试，需要复核消费者。选择范围与示例命令见[贡献指南](../../CONTRIBUTING.md#按改动选测试)。
- 每次扩大定向范围，选真实历史故障验证旧实现会失败、修复会通过，并在该变更提交上做一次完整回归。若全量发现定向遗漏，则补齐消费者和反例后重新评估。候选发行、标签和每周保留全量。对客户端、账号或资源操作的支持声明按[路线验收](../howto/route_acceptance.md)另行核实。

## 后果

日常修卡片识别可单独验证；同一修改涉及补星主循环、通用模板或扣费时仍要等待全量。维护者从 CI 日志记录定向耗时、全量升级原因和定向遗漏的故障，优先扩大反复发生、边界可验证的维护场景。

## 考虑过但被否掉的方案

| 方案 | 为什么没选 |
|---|---|
| 将整条路线文件直接加入快速名单 | 补星主文件还负责体力处理、开战和接力，卡片用例覆盖不了这些风险。 |
| 为每条路线先做一次统一拆分 | 大多数路线缺少故障回放与耗时对照，先按真实维护需求逐步登记。 |
