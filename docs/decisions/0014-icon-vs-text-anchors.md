# 0014. 「图标 + 中文名」的入口一律补白字候选，纯色图标改用多候选模板

## 背景

0013 修完大厅左侧菜单后，用户提出推广问题：全库还有哪些地方「既有文字又有图标、
却只看了图标」，能不能一起改成稳健的做法。同时问到项目已有 OCR，为什么这次用
「文字候选」而不是 OCR。

全库审计（`tools/_audit_icon_vs_text.py`，只读）：17 条路线 **264 个锚点** + 导航层
67 张模板逐个清点，按宽高比筛出 **63 张图标型**逐张目视分类，再在大厅、快捷菜单、
骑士团主页三处真实帧上核对控件全貌。

结论分四档：

- **已经在用文字**（不动）：`tower.home_enter`（只裁「入场」两字）、
  `knights_donation.points_label`（按行剖面切掉盾牌与数字）、
  `labyrinth_stone.region_row1_label`（「1 区域」）、
  `arena.weekly_reward_title`（用标题而不是宝石图案）、`lobby_activity`（图标 +「活动」）、
  `achievement_entry`、`craft_workshop_entry`、`lobby_hero`、`lobby_battle`、`lobby_sanctuary`。
- **纯图形、没有文字可用**（不改）：返回箭头、自动战斗开关、士气笑脸、地图商人 pin、
  三种书签商品图标、花瓣格、X 关闭、啤酒杯、暂停键。
- **看着像问题、实测不是**（不改）：`knights_donation.activity_entry` 图标上挂橙红圆点，
  本以为角标会打挂判据；实测 raw 有橙点 0.9259 / 无橙点 1.0000（阈 0.80），余量充足。
- **确属问题**（本次改）：5 处「图标 + 中文名」只裁了图标；另有一次对纯色图标误用白掩膜
  已撤回（见反面教材与「后续核查」两节）。

## 决定

### 一、五处补白字候选（纯加法，原样候选与阈值一字不动）

| 锚点 | 原模板 | 控件下方的文字 | 新增候选 |
|---|---|---|---|
| `lobby_knights` | 74×70 盾牌 | 骑士团 | `lobby_knights_text_white`（74×26） |
| ~~`lobby_side_story`~~ | ~~215×120 大图~~ | ~~支线故事~~ | ~~`lobby_side_story_text_white`~~ **已撤回** |
| `quick_menu_hero` | 65×57 天使徽记 | 英雄 | `quick_menu_hero_text_white`（51×27） |
| `quick_menu_knights` | 52×54 盾牌 | 骑士团 | `quick_menu_knights_text_white`（74×27） |
| `pet_house_entry` | 95×78 房子 | 宠物小屋 | `pet_house_entry_text_white`（99×27） |

统一走 `MATCH_MODE_WHITE_MASK` / 0.90，登记在 `EXTRA_WHITE_CANDIDATES`，
只在原样候选全部不过阈时才启用（沿用 0012）。

⚠️ `lobby_side_story` 一项**已整条撤回**：当初的立项依据是「新账号帧只有 0.7261
认不出」，而那是抓图通道错乱造成的假象，按正确通道重存后原样模板 **0.8945** 本来就
过阈（详见文末「后续核查」）。撤回范围包括：模板文件、`NavigationTemplates` 字段、
装配、`EXTRA_WHITE_CANDIDATES` 登记、以及对应的测试项。

顺带记下一条被这次撤回推翻的判断：曾认为「把那张 215×120 大图直接改白掩膜会更差
（0.8551 → 0.618）」—— 那个 0.618 是在通道错乱帧上测的，**不作为结论保留**。
该锚点维持原样，等 `docs/TODO.md` 里那条 EVENT 标裁剪的待办单独处理。

### 二、口径与阈值必须成对登记

新增 `WHITE_MASK_ANCHORS: dict[str, float]`，整颗锚点走白掩膜时，**门槛以表里为准**，
调用点传的 `threshold` 对它无效。理由：口径既然集中在一处，线也必须在一处，
否则同一个锚点有两个出处，改一处漏一处。

### 三、搜索区域下沿按文字位置重定

`quick_menu_knights` 由 670 放到 690、`pet_house_entry` 由 500 放到 515 —— 格子下方的
文字被原下沿切掉 3~7px，白字候选只能拿 0.119/0.125。放宽后原样分与落点**一字不变**
（0.9970 @(1591,584) / 0.9993 @(1570,385)），因为只是多了下方一片空白。

### 四、~~换号换配色的纯色图标改用多候选模板~~（**已撤回，见下一节**）

原先按「`lobby_quick_menu_button` 在 2026-11-21 那帧上只有 0.4685，形状一样、
配色从蓝换成橙」的判断，新增了一张橙版候选模板。当晚核查发现该帧是**抓图通道
错乱**，游戏里一直是蓝色，橙版模板已删除；`lobby_quick_menu_button` 退回单模板
（`_load_navigation_candidates` 结构保留，`_alt.png` 不存在时行为与单模板一致）。

## ⚠️ 反面教材：白掩膜对纯色块是**伪命中**

最初把 `lobby_quick_menu_button` 也登记进白掩膜表，实测三帧都是 1.0000，看起来完美。
实际是退化匹配：这颗图标是**纯色块**（B=235 / G=135 / R=68），白像素占比 **0.000**，
白掩膜后模板整块全黑，`TM_CCOEFF_NORMED` 拿全黑比全黑窗口会处处给 1.0，
落点漂到区域左上角 **(1821,75)** 而不是图标中心 **(1862,106)**，点击直接点空。
是导航测试断言点击坐标时才暴露的。

⇒ **立规矩**：给任何锚点登记白掩膜之前，先量模板的白像素占比；占比接近 0 就是
纯色图标，白掩膜对它无意义，换配色只能靠多候选模板。

## 实测数据

- 换底色（把非白像素整体换成暖褐/冷灰蓝/紫黑三色，白字保持不动，模拟真实主题变化）：
  四个锚点的原样模板掉到 **0.79~0.81**（阈 0.82，全部认不出），白字候选全部 **1.0000**。
- 紫黑主题帧：`lobby_knights` 0.6965 → 白字候选 **1.0000**。
- 排他：快捷菜单三格只在大厅菜单展开帧命中，普通大厅页上一颗都不响。

（原记录里「新账号帧 `lobby_side_story` 0.7261 → 0.9767」一条已删除：
该帧是抓图通道错乱，修正后原样 0.8945 本来就过阈。）

## ⚠️ 后续核查：三条改动被抓图通道 bug 推翻（2026-11-22 当晚）

当晚 `core/window.py` 修掉一个更底层的问题：**ADB 通道拿到的帧是 BGR，却被原样当成
RGB 使用**，于是经过 ADB 抓的帧 **R/B 通道互换**（蓝显示成橙、红显示成蓝）。
受影响的是 2026-11-21 抓的两张大厅帧（`lobby_menu_items_missing_20261121`、
`lobby_dark_portrait_live_20261121`）；更早的帧走雷电 Win32 抓图，通道是对的。

把这两帧按正确通道重存后逐条复核：

| 原结论 | 复核结果 | 处置 |
|---|---|---|
| 「换号把四格方块换成橙色，蓝版 0.4685」 | **假象**。通道互换后蓝版 **0.9979**，游戏里一直是蓝的 | 删除 `lobby_quick_menu_button_alt.png`，退回单模板 |
| 「`lobby_side_story` 新号帧 0.7261 认不出」 | 修正后 **0.8945**，本来就过阈 | **整条撤回**（模板 / 字段 / 装配 / 登记 / 测试项全删） |
| 「`lobby_knights` 紫黑帧 0.7140 认不出」 | 修正后 **0.6965**，仍不过阈；白字候选仍 1.0000 | 结论方向不变，保留 |
| 「`lobby_activity_alt` 覆盖新号形态」 | 方向对，但原模板**裁自错乱帧**，颜色是错的 | 按修正帧重裁（避开 N 角标），全库 470 帧仅来源帧 ≥0.80 |
| 「左侧菜单整列上移约 93px」 | 修正后 `lobby_shop_entry` 仍只有 0.6434、`lobby_sanctuary` 0.7415 | 与通道无关，0013 的结论站得住 |

**处置原则（用户 2026-11-22 明确）**：被错图误导的改动一律**还原**，不做任何优化式
替代；只有「本来就不过阈、且与抓图无关」的才保留。

修正后的四个大厅帧实测（`lobby_shop_entry` / `sanctuary` / `activity` 在新号帧上
分别 1.000 / 1.000 / 1.000，全部由候选兜住；`quick_menu_button` 0.998~1.000）。

**新立的规矩**：任何「某处外观变了」的结论，先排除抓图口径 —— 用同一张模板在
同批帧上做一次**通道互换对照**。互换后能上到阈上，就是图的问题，不是游戏的问题。

## 后果

收益：
- 「图标 + 中文名」的入口不再随图标挂角标、随主题变暗、随底图换色而失效；
- 判据回到「人眼找按钮」的依据上：文字不会变，图标会。

代价（**接受了**）：
- 每个锚点多一张模板、多一次匹配，只在原样候选失败时才付这笔钱；
- 纯色图标若真出现第二种长相（与抓图口径无关的那一类），仍需累积候选模板，
  这是图片方案的固有限制；
- 白掩膜要求文字**确实是白的**：整体调暗（而不是换底图）会让它一起失效，
  这类主题不在覆盖范围内。

## 考虑过但被否掉的方案

| 方案 | 为什么没选 |
|---|---|
| 全部锚点统一改白掩膜 | 纯色图标会退化成永真（见反面教材）；按钮类模板底色占比高，换尺子要逐颗重定阈值，收益不抵风险 |
| 用 OCR 读这些入口文字 | 判据问题不是读数问题；OCR 单次 0.35~1.1 秒，判页每帧都要跑会拖垮节拍 |
| 把 `lobby_side_story` 那张 215×120 直接改口径 | 当初记的「0.8551 → 0.618」测自通道错乱帧，**数据不作数**；该锚点维持原样，等 EVENT 标裁剪那条待办单独处理 |
| 给 `lobby_quick_menu_button` 走低通口径 | 修正通道后实测 0.9326 / 0.9303 / 0.9324，**比原样 0.998 更低**；原先那组 0.4163/0.4428 是在通道错乱帧上测的，不算数 |
| 纯色图标改固定坐标点击 | 位置虽稳，但与「不写死坐标」的原则冲突，且换分辨率/窗口尺寸即失效 |
