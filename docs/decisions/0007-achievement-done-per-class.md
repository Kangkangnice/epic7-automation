# 0007. 成就领取的收工判据改成「逐个分类走进去确认」，不再看角标红点

## 背景

2026-11-08 每日任务最后一步「成就领取」21:16 报成功（汇总打勾），用户点开成就页却看到
**有一个分类还剩 10 个成就没领**。

查到的机制：

- 旧收工判据是**一句话**：左边 4 个分类图标上都没有角标红点 ⇒ 收工。
- 但红点只表示「这个分类有新达成的成就」，**不代表「没有奖励可领」**。
  仓库里的现场帧 `tests/fixtures/epic7_achievement_pc/page_alive_pc_live_20261108.png`
  就是反例：当前分类图标上**没有红点**，但右下「全部领取」是亮的、列表里四条都写着「领取」。
- 而旧实现只对**当前停留的那个分类**检查「全部领取」颜色和「持续效果上升」按钮，
  另外 3 个分类**只数红点、从不走进去看**。于是只要某个分类的红点先消失，
  程序永远不去确认它的按钮，那里剩多少都跟程序无关 —— 收工时它自己也不知道。

用户给的结束标志是三条：**红点都没了 + 没有升级按钮 + 全部领取也灰了**。
旧实现只把第一条用在了「整体收工」上，后两条只对当前分类生效。

## 决定

> ⚠️ **本节的 `_settled` / 连续 3 帧 / 原地复核是初版写法，三次实跑证明落不了地，已作废。**
> 现行实现见下方「实现演进：三次实跑后的定稿」：`_visited` + 画面指纹同帧幂等 +
> 切分类短等待。**决策本身没变**：收工必须逐类亲眼看过，红点只决定先去哪个、不决定去不去。

收工 = **4 个分类逐个走进去确认**「全部领取灰 + 没有升级按钮」，全部确认过才 DONE。
`_settled` 记录已确认的分类，红点只用来决定**先点哪个**，不再决定**去不去**。

三个落地细节：

1. `_GRAY_FRAMES_TO_SETTLE = 3`：连续 3 帧「灰 + 无升级按钮」才记进 `_settled`。
   依据是 `TRANSITION_CONTRACTS` 的结论门槛（跳过某个环节也要连续两帧）；
   取 3 而不是 2，是因为刚切分类那一两帧画面可能还没加载完，
   而灰帧的代价是「这个分类整条漏掉」。
2. 没确认完就**留在原地复核**，不要每帧都切走 —— 每帧切走的话永远等不到第 3 帧。
   点同一个分类图标是幂等的（不会改变选中项）。
3. `_pick_class` 只在「还没确认过」的分类里挑，优先有角标的、且不是刚点过的。

明确不做：不新增「逐条点领取」的能力。目前没有证据说明存在「全部领取灰了但列表还有
可领」的情况；如果将来出现，那是另一个决定（需要先有现场帧）。

## 后果

- **接受了的缺点**：一轮会多花 4 × 3 ≈ 12 帧（约 6~12 秒）做复核，即使本来就已经领干净。
  换来的是「不会再把整个分类漏掉」。
- **收益**：收工这件事第一次有了「对每个分类都亲眼看过」的证据，而不是靠一个间接指标。
- 旧测试 `test_no_dots_anywhere_means_done_and_counts_one_cycle` 被**替换**成
  `test_done_requires_all_four_classes_confirmed` + 一条反向护栏
  `test_no_dots_does_not_mean_done_on_the_very_first_frame`
  （喂「一帧无角标」，断言不许收工 —— 正是这次事故的形态）。

## 考虑过但被否掉的方案

- **保留红点判据，只补「另外三个分类也看一眼按钮」**：等于把判据拆成两套，
  红点那条依然是错的（它回答不了「有没有可领」），迟早还会漏。
- **只把 `_MAX_SWITCHES` 调大**：治不了根 —— 红点消失的分类根本不会被选中，
  调多少次都轮不到它。

## 实现演进：三次实跑后的定稿（2026-11-08 23:22）

> 上面「决定」节里的 `_settled` / `_GRAY_FRAMES_TO_SETTLE = 3` / **原地复核**是初版写法，
> 三次真机实跑证明它落不了地，**已由本节形态取代**。决策本身没变：
> 收工必须逐类亲眼看过、红点只决定先去哪个、不决定去不去。

| 版次 | 做法 | 实跑结果 |
|---|---|---|
| 初版 | 连续 3 帧「灰 + 无升级按钮」才记进 `_settled`；没确认完就**点同一个分类图标**原地复核 | 点已选中的图标不产生任何画面变化，主循环等「动作名/页面变了」烧到 42 秒超时，把整条路线判成完成 |
| 二版 | 复核帧数降到 1，改成每帧直接切下一个分类 | 主循环在**同一帧**会重复问 `next_action`，每次都把 `_settled` 往上推一格，一帧内凑满 4 个 ⇒ 还是提前收工 |
| **定稿** | `_visited` 只记「点进去过哪个分类」+ 画面指纹同帧幂等 + 切分类短等待 | 23:22 实跑四个分类逐个进入，`EXIT 0`，总耗时约 21 秒 |

定稿的四条落地细节：

1. **判据简化成 `_visited: set[int] = {0}`**。要证伪的是「有没有进去看过」，不是
   「这个分类灰了几帧」—— 每切一次分类必然带来一帧新画面，当帧的「全部领取灰 +
   没有升级按钮」就够把当前分类记进 `_visited`。收工 = `len(_visited) >= CLASS_COUNT`
   （`_MAX_SWITCHES = 20` 仍留着兜底）。
2. **同帧幂等**：`_frame_key()` 把画面下采样 8 倍算 MD5（6.7 MB → 105 KB），
   `next_action()` 用 `_last_frame_key` / `_last_action` 缓存同一帧的答案。
   主循环一轮里问几次都不再推进业务进度。⚠️ 指纹**只用于去重**，不参与任何判据。
3. **绝不留原地复核**：`switch-class` 每次都挑一个**还没进去过的**分类，
   点下去必然换画面，主循环才等得到转场。
4. **把切分类从约 46 秒压到约 8 秒**：`AchievementRunner._SHORT_RETRY_ACTIONS`
   原先只是个声明，基类 `_action_retry_seconds()` 根本不读它（直接返回 45 秒）；
   补上钩子接线，并把 `switch-class` 加进集合（`_SHORT_RETRY_SECONDS = 8.0`）。
   这是「转场开关挂着不等于生效」的又一例。

`preview` 的快照同步改成含 `_visited` / `_current_class` / `_last_frame_key` / `_last_action`，
保证「预览一眼」不会偷跑进度。回归测试见 `tests/test_achievement.py`。
