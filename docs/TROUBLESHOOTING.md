# 故障排查

## 先保留现场

自动化停止时，不要立刻关闭模拟器、删除日志或重新启动脚本。先记录运行命令和屏幕状态，再检查：

- 文件日志：`runtime_logs/epic7_<mode>.log`
- 当前帧：`runtime_diagnostics/epic7_<mode>/current.png`
- 失败诊断：同一目录下带故障原因的 PNG

终端日志与文件日志同步输出。排障时重点看最后一次已执行动作、等待的目标页面、重试次数和停止原因。

## 退出码

| 退出码 | 含义 | 下一步 |
| --- | --- | --- |
| `0` | 已达到目标循环数 | 无需处理 |
| `1` | 未知页面、转场失败、黑屏或运行故障 | 保留日志和截图，补回归样本 |
| `2` | 允许的资源耗尽 | 检查资源规则是否符合预期 |
| `130` | 用户按 `P` 手动停止 | 正常人工中断 |

## 页面无法识别

表现：日志长时间停在同一状态，最后报告 `no progress`、`expected ... anchor` 或保存 `timeout_*.png`。

检查顺序：

1. 打开 `current.png`，确认它确实是游戏窗口，不是黑屏、桌面或遮挡。
2. 对照日志中的当前状态，确认实际页面与状态机预期一致。
3. 检查游戏 UI、语言、模拟器尺寸和宽高比是否变化。
4. 比较失败截图与 `tests/fixtures/` 的已有页面。
5. 如果是新页面，先保存完整截图并写失败测试，不要直接降低全局阈值。

## 路线开局没有回大厅，直接从中间开始跑

这是**预期行为**，不是故障。竞技场、主线和远征实跑启动时都会先认画面，停在半路就从那一步接着跑，只有停在别的页面才受控返回大厅。用这三样东西确认：

- 日志里的 `模式=arena|story|expedition 开局=接力 页面=… 落点状态=… 动作=跳过回大厅与路线导航`（探针命中那一刻）
- 日志里的 `模式=导航 开局=接力 页面=… 动作=跳过回大厅与进入… 状态=…`（命中点已经在导航链的某一级上时，由 `navigate(already_at=...)` 补一条）
- 同目录下的 `*_resume_point.png` 诊断图（接力那一刻的现场）

各路线能接力的画面：

- **竞技场**：竞技场模式选择 / 对战详情 / 准备战斗 / 对手列表 / 战斗结果页 / 结果确认中（段位提升弹窗）/ 局内。局内接力不会按 `Back`，只是把这一局交给战斗监督；只有「买票弹窗压住的队伍页」不接力（走老流程）。
  结果页/确认中这两步的计数口径：落在「结果确认中」时这一轮算你已打完，回到列表就 +1；落在「战斗结果页」时确认还得由助手点，那一轮照常走完再 +1。两种落点都只 +1 一次。
- **主线**：关卡入口、队伍准备、助手选择、剧情播放、跳过确认、通关提示、额外奖励、各类结算页；局内也接力，但只是把这一局交给战斗监督，**不会按 `Back`**。
- **远征**：战斗菜单 / 赛季菜单 / 远征主页，以及通缉传单、难度确认、公开招募、队伍选择、结算等业务页。

如果它认错了页面（诊断图和日志里的页面名对不上），把该 PNG 按 fixture 规范补进对应目录并**先写失败测试**，再调判定顺序或锚点区域，不要直接放宽阈值：

- 竞技场 → `tests/fixtures/epic7_arena/` + `arena._ARENA_RESUME_ORDER`
- 主线 → `tests/fixtures/epic7_story/` + `story._STORY_RESUME_ORDER`
- 远征 → `tests/fixtures/epic7_expedition/` + `expedition._EXPEDITION_RESUME_ORDER`

调顺序时注意：**顺序即优先级**（同页可见的锚点，排在前面的赢）。竞技场 `SELECTED` 必须在 `LIST` 前；主线 `prepare_battle`/`watch_story` 和 `complete` 必须在 `next_stage` 前；远征 `HOME` 必须在 `RETURNING` 前、`OUTCOME` 必须在 `READY` 前。

想让路线**别走接力**（强制走「一路返回大厅 → 按路线重新导航进去」那套，用来复现接力挂上之前的行为）：
把游戏切到任意非本路线的页面即可 —— 探针扫不到接力点，就会一路返回到大厅再重新导航（竞技场、主线、远征同理）。

## 点击后没有转场

表现：同一动作显示 `尝试=1/4` … `尝试=4/4`，随后安全停止
（2026-09-26 起**不再**回大厅恢复；路线会先有一次**原地**「换个办法」的机会，
换回来还是同一个动作就直接停）。

可能原因：

- 模拟器卡顿，第一次点击未生效。
- 点击时页面仍在加载或按钮被弹窗覆盖。
- 模板中心不是安全点击区域。
- 实际已转场，但目标页面锚点不稳定或搜索区域错误。

查看失败诊断，分别确认“点击前按钮是否存在”和“点击后目标页面是否出现”。不能用增加连续点击次数掩盖目标页识别问题。

## 黑屏、遮挡或非游戏画面

程序只截取标题为“第七史诗”的窗口。持续黑屏、窗口最小化、渲染异常或前台被覆盖时会安全停止。

1. 确认游戏窗口存在且未最小化。
2. 确认模拟器仍使用已校准的分辨率和宽高比。
3. 手动切回游戏并等待画面稳定。
4. 先运行不带 `--live` 的干跑确认识别，再重新实跑。

不要在自动化期间使用鼠标键盘或把其他窗口盖在游戏上。

## 战斗 HUD 暂时消失

技能动画可能完全遮住右上角 HUD。只要截图仍是有效游戏帧且战斗区域持续变化，Runner 会继续运行并输出：

```text
页面=战斗中 状态=心跳 HUD暂时隐藏
```

这不是故障。只有战斗画面持续无进展达到上限，或超过单场绝对时间上限，才会保存诊断并停止。

## P 键没有立即停止

P 键在轮询边界检查，不保证在一次截图或系统调用中间立即打断。保持游戏前台，短按一次 `P`，等待终端输出手动停止。不要连续按键或直接关闭终端，除非进程本身已经失去响应。

## 界面点了「安全停止」一直不退

和上面那条是同一个机制：**停止是在两次动作之间读一次信号**，不打断进行中的那一次调用。
平时它 1~2 秒就退（8-31 ~ 9-28 的日志里 88 次都是这样），但如果它此刻正卡在**一次底层
调用的内部**，就永远轮不到读信号 —— 界面会一直停在「正在安全停止」，信号文件写下去了也
没人读。

**2026-09-28 起有兜底**：点过「安全停止」后等 **30 秒**（`desktop/app.py::STOP_GRACE_SECONDS`）
还不退，助手会**强行结束**这个运行，并在日志里写「已强行结束这个卡住的运行」。
⚠️ 强行结束会跳过回家流程，游戏可能停在半路 —— 所以它是**第二手**，不是常用路径，
宽限期也刻意给得很宽（正常路径的十几倍），免得误杀正在正常收尾的运行。

判断「卡死了」还是「还在跑」，按这个清单走：

1. `runtime_logs/desktop_worker.log`：有没有 `事件=结束`；`事件=停止请求` 之后有没有后续。
   两次「停了但没结束」的现场都长这样（2026-09-07 20:02:11、2026-09-28 07:44:33）。
2. 采样子进程 CPU 两次（隔几秒）：差值为 0 ⇒ 卡死（真在跑一定会动）。
3. `%TEMP%\epic7-auto-assistant-*` 下有 `stop.signal`、而进程没退 ⇒ 信号写了没人读。
4. 有没有孤儿 `adb.exe`，启动时间是否正好压在最后一条 `执行点击` 上。

为什么容易卡在那里：**发点击走 `adb`**，那条通道不健康时调用会一直等下去（`device offline`
是已确认反复复发的环境问题，项目记忆 `topics/click_channel.md` 有完整记录）。所以卡住时先看
模拟器在不在、`adb devices` 是不是 `offline`；开跑前的自检只管「一开局就是坏的」，
管不到「跑起来之后发点击才卡住」。

⚠️ **还没修的一条**：截图侧（`PrintWindow`/`GetDIBits` 对已死窗口的跨进程 GDI 调用）同样能
无限阻塞，症状与「卡在发点击」一模一样，没有线程栈区分不了 —— 要真正治本得给那条调用加
**能生效的**超时（现在代码里的 `timeout=` 在「套娃命令」下拦不住，超时只杀掉外层进程，
内层还占着输出管道）。这要改 `core/window.py`。

## 提交有效问题现场

反馈给后续 AI 时提供：

1. 完整运行命令。
2. 发生问题的大致时间和你看到的页面。
3. 日志最后 30 行。
4. `current.png`。
5. 最新的失败诊断 PNG。
6. 你认为正确的下一步动作，以及该动作是否允许消耗资源。

AI 应先解释最后状态和证据，再要求用户操作到一个明确页面；未经授权不得自行控制模拟器。
