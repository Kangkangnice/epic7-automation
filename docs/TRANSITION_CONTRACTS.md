# 页面转场契约

自动化中的一次点击不等于业务成功。每个会改变页面或业务状态的动作，都应当写清楚“允许从哪里点击、看到什么才算进入、看到什么才算完成、失败时留下什么证据”。这份约定用于新路线开发、现有路线审计和实机故障复盘。

## 基本原则

总原则是：**点击不等于成功**，安全结论必须明确属于 `SAFE / UNSAFE / UNKNOWN` 三态之一。

1. **点击只是候选动作**：日志只能写“已点击/等待确认”，不能在目标证据出现前写“成功”。
2. **先确认来源，再允许点击**：来源页面不明确时，不靠坐标猜测；返回 `UNKNOWN` 并保存诊断。
3. **安全判断采用三态**：
   - `SAFE`：正向证据充分，可以继续。
   - `UNSAFE`：发现明确阻断证据，必须停止或转入安全分支。
   - `UNKNOWN`：证据缺失或互相冲突，不得按 `SAFE` 处理。
4. **缺少模板时关闭危险动作**：涉及选择材料、传送、消耗资源等动作，关键模板缺失必须 fail closed。
5. **确认目标来自原事务**：重试时保留第一次点击的目标页面和业务目的，不能用当前误识别页面覆盖原目标。
6. **动态区域不能单独证明切换成功**：人物呼吸、粒子、滚动动画只能作为“发生过运动”的辅助证据；成功仍需稳定页面标志或业务状态变化。
7. **进入与退出都要稳定**：建议在连续稳定帧或等价的去抖条件满足后确认页面，避免单帧误判。
8. **循环计数只跟业务完成绑定**：点击次数、过渡动画和重试次数都不能增加完成轮次。
9. **日志必须可证伪**：记录候选动作、来源证据、目标证据、重试原因和最终结论；“未确认”不能写成“成功”。
10. **下结论也要去抖**：不只动作要连看两帧，**宣布收工、宣布认不出画面、跳过某个环节**同样要连续两帧一致才采信。细则与强制方式见下一节。

## 结论门槛（全局强制）

> 2026-09-25 实跑当场抓到两条事故，都是**一帧**惹的祸：
> - 世界首领战：主页判「今天没场次了」的异常从 `preview()` 直接穿到主循环，早于两帧确认 ⇒ 一帧就宣布整条路线收工，宝箱还没看就说打完了；
> - 通用：`UnrecognizedScreen` 同样一帧穿出去 ⇒ 一帧没认出画面就去点屏幕中间。
>
> 上面第 7 条早就写了「避免单帧误判」，但**只管住了动作，没管住结论** —— 动作要两帧、结论只要一帧，门等于只掩了一半，而真正会终止路线的恰恰是这些结论。所以这一节不是建议，是强制。

### 什么算「下结论」

| 结论 | 例子 | 以前 | 现在 |
|---|---|---|---|
| 宣布收工 | 资源/次数耗尽（`ResourceExhausted` 及其子类）、票没了、传单没了 | 一帧 | 连续两帧一致 |
| 宣布认不出画面 | `UnrecognizedScreen` | 一帧（随后去点屏幕中间） | 连续两帧一致才允许唤醒 |
| 跳过某个环节 | 材料不足 / 支援上限已满 / 按钮已灰 | 各路线自定 | 同一道门槛（接线中的路线） |

### 规矩

1. **连续两帧一致才采信**：同一结论要在相邻两帧上看到，才允许按它行动（收工、唤醒、跳过）。
2. **换结论就重新数**：第一帧缺这个、第二帧缺那个，是两次误判，不是一次确认。
3. **换页 / 恢复 / 黑屏后清零**：跨页面的两帧不算「连看两帧」。
4. **被拦下的结论必须写日志**：日志里出现「结论待确认=…」，不许哑判 —— 实跑复盘全靠它。
5. **唯一例外 `ManualStop`**：那是用户按了停止键，不是程序下的结论，必须立刻响应。

### 落地位置

| 层 | 位置 |
|---|---|
| 门槛本体 | `core/supervisor.py::ConclusionGate`（`admit(error)` / `reset()`） |
| 接线（走基类主循环，6 条路线） | `games/epic7/runner_base.py::ModeRunnerBase._stable_next_action` |
| 接线（**事务型**基类的 `run()`，远征） | `games/epic7/transactional_runner_base.py::TransactionalRunnerBase.run` |
| 接线（继承**事务型**基类、但自带 `run()`，竞技场） | `arena.py::ArenaRunner.run` —— 2026-09-26 起继承 `TransactionalRunnerBase`（共享转场验收、失败诊断、战斗移交、收尾骨架），**循环策略不同所以保留自己的 `run()`**，结论门槛接在那儿 |
| 非「每帧下结论」形态的路线 | `shop_refresh` / `survivor`：结论都在 `_wait_stable` 稳定之后或超时之后，见 `modes.CONCLUSION_GATE_DECLARATION` |

### 护栏（两道，缺一不可）

1. **路线准入**：`modes._assert_conclusion_gate_declared()` —— 每条路线要么走基类门槛、要么在 `CONCLUSION_GATE_DECLARATION` 里写明「自己靠什么保证」。重写 `_stable_next_action` 却不调 `super()` 视为绕过。
2. **跑真主循环的反向测试**：`tests/test_conclusion_gate.py` —— 喂「只看到一帧」的结论，断言**不许收工、不许点屏幕中间**；连喂两帧才允许收工。只调校验方法的测试挡不住「接线被摘掉」。

### 元规范：一条规范怎么才算「做完」

> 2026-09-25 的教训不是「没人写规范」，而是**规范写在文档里、代码里没人执行**，两年都没人发现。

今后任何一条新规矩，交付时必须同时具备三样，缺一样就当没做：

1. **文档**：写清规矩和理由（本节这种写法）；
2. **代码门槛**：违规时程序**自己拒绝**，而不是靠人记得（`ConclusionGate` / `_REQUIRE_TRANSITION_CONTRACT` / 加载期 `assert` 都属此类）；
3. **护栏测试**：**反向**喂违规输入，断言被拦下 —— 正向测试只证明「照做能跑」，反向测试才证明「不照做跑不了」。

## 点击后的观测决策

点击后不能依靠一次性 `clicked=True` 等待超时，必须继续判断来源和目标：

| 稳定观测 | 含义 | 允许动作 |
|---|---|---|
| 来源仍在，目标未到 | 点击未生效 | 记录来源证据，在额度和冷却满足后重试 |
| 来源已离开，目标未稳定 | 正在转场或结果待确认 | 只等待，禁止重复旧动作 |
| 目标稳定进入 | 转场完成 | 记录来源退出和目标进入，进入下一状态 |
| 来源与目标冲突，或两者均无法判断 | `UNKNOWN` | 保存证据并失败关闭或执行契约声明的有限恢复 |

可逆导航动作只在来源仍稳定时重试。不可逆动作在来源消失后不得重试，因为业务可能已经执行而回执尚未出现。来源、目标和业务结果必须分别去抖；一个目标帧不能倒推此前每次点击都成功。

## 契约模板

实现或审查一个动作时，复制并填写以下字段：

```text
动作名称：
来源页面：
进入正向证据：
阻断证据 / UNKNOWN 条件：
点击坐标依据：
允许目标页面：
业务成功证据：
重试条件：
失败诊断：
循环计数影响：
```

字段说明：

- **来源页面**：动作被允许执行的页面状态。
- **进入正向证据**：确认已进入来源页面的稳定视觉或状态证据。
- **阻断证据 / UNKNOWN 条件**：明确危险标志、关键模板缺失、识别冲突或证据不足。
- **点击坐标依据**：固定布局、模板中心或经窗口缩放换算后的逻辑坐标。
- **允许目标页面**：点击后可以合法抵达的页面集合。
- **业务成功证据**：能够证明业务结果已经发生的证据，而不是动画或局部变化。
- **重试条件**：来源仍成立、目标未出现且未发现危险状态时，才允许重试。
- **失败诊断**：至少保存最终截图；高风险或难复现动作应保存前后帧、裁剪区和量化指标。
- **循环计数影响**：说明何时加一，通常只有业务完成证据成立时才加一。

## 推荐日志语义

```text
动作候选 action=<name> source=<page> evidence=<summary>
执行点击 action=<name> attempt=1/4 point=(x,y) targets=<pages>
等待确认 action=<name> observed=<page> remaining=<seconds>
转场未确认 action=<name> reason=<reason> retry=<n/4>
转场确认 action=<name> target=<page> evidence=<summary>
业务成功 action=<name> result=<result> cycle=<n>
安全停止 action=<name> state=UNKNOWN diagnostic=<path>
```

“转场确认”和“业务成功”是两个不同层次。例如进入合成页面只证明页面切换完成，只有结果页出现并被正确关闭后，才证明一次合成事务完成。

## 英雄合成示例

### 切换英雄卡片

- 来源页面：英雄详情/列表中的当前英雄卡片稳定可见。
- 进入正向证据：中心选中框、详情区域和列表结构满足英雄详情页条件。
- 点击坐标依据：下一张英雄卡片的固定槽位或经过标定的逻辑坐标。
- 允许目标页面：仍为英雄详情页，但选中事务必须经历可解释的切换过程。
- 业务成功证据：过渡动态已经结束，详情页重新稳定；能区分时使用身份特征，两个副本外观相同时不能只比较英雄立绘。
- 重试条件：点击后既未观察到切换动态，也未观察到稳定目标状态，并且来源页面仍成立。
- 失败诊断：保存点击前、动态峰值帧、点击后稳定帧和各 ROI 差异指标。
- 循环计数影响：无。

### 进入合成

- 来源页面：目标英雄详情页。
- 进入正向证据：合成/记忆刻印入口可操作，页面无弹窗遮挡。
- 阻断证据 / UNKNOWN 条件：入口置灰、页面身份不明或关键模板缺失。
- 允许目标页面：合成材料选择页。
- 业务成功证据：材料区域、确认区域等合成页稳定标志同时成立。
- 重试条件：详情页仍成立且目标页未出现。
- 循环计数影响：无。

### 选择材料

- 来源页面：合成材料选择页。
- 进入正向证据：材料卡区域和确认区域稳定可见。
- 阻断证据 / UNKNOWN 条件：任一候选材料识别为 SSS，或 SSS 判断证据不完整。
- 业务成功证据：安全材料已进入选中状态；仅“看见材料卡”不等于可以点击。
- 重试条件：只能在安全判定仍为 `SAFE` 时重试。
- 失败诊断：保存材料卡原图、SSS 检测区域、匹配分数和候选排序。
- 循环计数影响：无。

### 遇到 SSS 后退出并传送副本

- 来源页面：合成页或英雄详情页，且目标英雄已确认达到 SSS。
- 进入正向证据：SSS 为稳定正向证据，不依赖单帧动画。
- 点击坐标依据：先退出合成页，再进入传送流程；每一步单独确认。
- 允许目标页面：英雄详情页 → 传送选择页 → 传送确认/完成页。
- 业务成功证据：传送完成结果出现，随后回到允许的英雄页面。
- 重试条件：只对当前尚未确认的转场重试，不重复已经确认的消耗动作。
- 循环计数影响：按英雄处理事务定义计数，不按退出或点击计数。

### 关闭合成结果并返回列表

- 来源页面：合成结果页。
- 进入正向证据：结果标题或结果主体稳定出现。
- 允许目标页面：英雄详情页或英雄列表，以动作契约声明为准。
- 业务成功证据：结果页消失且目标页面稳定出现；不能用“已点击关闭”替代。
- 重试条件：结果页仍存在时可重试关闭；已经离开结果页时不得盲点原坐标。
- 失败诊断：保存结果页、点击后页面和最终超时截图。
- 循环计数影响：仅当本次合成结果已确认且收尾页面成立时完成事务。

## 模拟器刷书签示例

### 扫描一批商品

- 来源页面：秘密商店商品列表稳定可见，标题、`立即更新=3` 与同行购买按钮结构同时成立。
- 扫描顺序：先扫描顶部；随后执行一次列表滑动，只有观察到列表内容发生明显变化并重新稳定，才允许扫描底部。
- 阻断证据 / `UNKNOWN`：目标图标成立但同行购买按钮缺失时，只有该槽位刚刚完成过购买才可解释为“已售”；否则立即停止，不把识别不完整当成普通商品。
- 循环计数影响：顶部和底部都扫描完才完成一个批次；初始批次不计入付费刷新次数。

### 打开并确认购买

- 来源页面：誓约书签或神秘书签图标成立，且同一商品行的购买按钮可操作。
- 允许目标页面：与来源商品类型一致的购买确认框。
- 可逆重试：打开确认框后若目标未出现，只有原商品和同行购买按钮仍成立时才允许受限重试。
- 不可逆动作：购买确认最多点击一次；确认框离开后只等待业务结果，不再点击原确认坐标。
- 业务成功证据：购买框已经离开，原槽位仍能识别为同种书签但不再有可操作购买按钮；此时才分别增加誓约或神秘的购买次数与金币花费。
- 阻断证据 / `UNKNOWN`：确认框商品类型冲突、回执不明确、未知弹窗或未购买过的目标槽位缺少购买按钮时保存诊断并停止。

### 打开并确认付费刷新

- 来源页面：本批顶部和底部均扫描完成，且秘密商店的 `立即更新=3` 按钮稳定可见。
- 允许目标页面：当前客户端刷新确认框。
- 可逆重试：打开确认框失败时，仅在 `立即更新=3` 来源仍成立时受限重试。
- 不可逆动作：刷新确认最多点击一次；确认框离开后不得再次点击确认。
- 业务成功证据：确认框先离开，随后商品列表发生变化，并以不同于刷新前的列表指纹重新稳定为商店顶部。确认弹窗本身的变化不计为刷新动态。
- 循环计数影响：只有业务成功证据成立才增加一次付费刷新并记入 3 钻石；最后一次刷新后的新批次仍必须完整扫描。

### 本轮统计与安全边界

- 输入 `N` 表示执行 `N` 次付费刷新，共扫描初始页面加刷新后的 `N` 个页面，即 `N + 1` 批。
- 初始页面与付费刷新页面的誓约、神秘购买次数分开记录；付费命中率不包含初始页面。
- 只保留本轮日志汇总，不写历史统计文件。
- 金币不足停止整条路线；钻石不足停止后续刷新。当前不足资源页面尚无当前客户端固定样本时，未知弹窗按 `UNKNOWN` 安全停止。
- 首版只支持雷电模拟器；PC 后端在创建窗口和执行动作前明确拒绝。
- 誓约与神秘书签均已有当前客户端商品行、购买价格和购买后 `0/1` 已售槽位固定样本；两种真实购买事务均完成回放测试。代码不会把业务预期价格伪装成视觉结果；空跑仍输出候选类型、分数和同行购买按钮，供游戏更新后的重新验收。

日志示例：

```text
模式=刷书签 动作候选=purchase 来源=商店顶部 目标=誓约书签 行=2
模式=刷书签 转场确认 动作=open_purchase_confirm 目标=誓约书签购买确认
模式=刷书签 执行不可逆动作=confirm_purchase 目标=誓约书签 尝试=1/1
模式=刷书签 业务成功=购买 目标=誓约书签 本轮次数=1
模式=刷书签 执行不可逆动作=confirm_refresh 尝试=1/1 价格=3
模式=刷书签 业务成功=刷新 已完成=1/10 钻石花费=3
```

## 模拟器竞技场示例

### 选择对手与点击挑战

- 来源页面：含安全对手的列表，或已经选中的对手详情。
- 点击坐标依据：首次选择后固定本轮对手行与坐标；重试不得重新随机选择。
- 允许目标页面：对手详情，或普通/快速队伍页。
- 重试条件：来源连续存在且目标未成立时最多四次；任何一帧确认来源离开后不再点击旧坐标。
- 业务成功证据：目标页面连续两帧；单次按钮匹配或执行点击日志均不代表成功。

### 快速战斗切回普通战斗

- 来源页面：快速战斗按钮和白底闪电切换键同时成立，普通战斗开始按钮不成立。
- 允许目标页面：路线自己的普通战斗开始锚点连续两帧。
- 共享范围：模拟器主线、竞技场、远征和狗粮；PC 后端仍为实验开发范围。
- 重试条件：快速来源仍在时受限重试；来源离开后只等待普通页。

### 开启自动战斗

- 来源页面：战斗结构稳定，且右上角“自动关闭”图标连续两帧成立；不等待轮到我方出手。
- 动作：点击“自动关闭”图标中心，请求开启自动战斗。
- 允许目标：右下角人物头像布局连续两帧，蓝色、红色或混合头像均可。
- 重试条件：右上角关闭图标仍在时有限重试；关闭图标消失而人物头像暂未稳定时只等待，不再点旧坐标。
- `UNKNOWN`：敌方连续行动、技能动画或我方技能尚未出现都属于正常等待，不再使用 15 秒自动确认超时；仍受战斗无活动、业务无进展和绝对时限保护。

### 战前业务弹窗优先级

- 战前业务弹窗一旦出现首帧，立即冻结并重置已经稳定的背景白名单动作；不得在等待第二帧期间点击被遮罩后的“战斗开始”等旧控件。
- 业务弹窗连续两帧成立后才交回路线状态机；若只闪现一帧，背景动作必须从零重新满足稳定条件。
- 路线观察层应避免同时上报业务弹窗和背景动作，共享战斗监督器仍须独立执行相同保护。

### 刷新、旗帜与结算

- 刷新只在三名对手均明确不可挑战时执行；免费确认必须同时识别标题、“免费”和确认按钮，刷新后列表还要连续两帧且至少有一名安全对手。
- 首轮无票和中途耗尽共用同一购买事务：点击战斗开始后，购买框首帧先冻结背景动作，连续两帧后再进入购买判断。
- 友情点购买只接受左侧已选中的“100 友情点换 5 旗帜”：购买弹窗标题、固定报价与黄色选中框、购买按钮必须同时成立；动态“持有”余额不参与识别，右侧“30 钻石换 5 旗帜”永久禁止。购买弹窗仍在才允许重试，弹窗离开后不重复不可逆点击，目标队伍页稳定后才写入当天购买记录。
- 结果确认允许进入段位弹窗或直接回到列表；结果页仍在时有限重试，结果页消失后不盲点。
- 循环计数只在结算事务结束并连续两帧回到对手列表后增加，刷新列表不计数。

执行点击 动作=challenge 坐标=(x, y)

## 审查清单

- 动作是否同时定义了来源页面和允许目标页面？
- 危险动作是否有 `UNKNOWN` 分支，而不是把识别失败当作安全？
- 日志中的“成功”是否都有对应的业务证据？
- 相同外观、动态动画和弹窗遮挡是否会制造假阳性？
- 重试是否保持原目标，并避免重复执行不可逆动作？
- **点击后的落点里，有没有「必须先处理掉才能继续」的中间页（尤其模态弹窗）？**
  有的话它**必须**写进**上一个动作**的 `target_pages` —— 否则处理它的那个动作永远发不出去：
  转场未成立 ⇒ 主循环把当前动作置成 `None` 丢弃（见 `runner_base.run()` 里
  `elif last_transition_action is not None:` 那段）⇒ 中间页没人处理 ⇒ 干等到状态超时。
  2026-10-15 支线故事「完成故事」弹窗就是这么挂的（判据 0.9995 命中、动作也生成了，
  但日志里从点击到超时一个动作都没有）。
- **上一条不只管「中间页」，也管「终点页」**（2026-10-18 主线 `retry_stage`）。
  结算确认点完可能落到「无法前往下一关」（重复打同一关的常态终点页）——
  它不需要再往前推进，但**必须先在 `results_confirm.target_pages` 里登记**，
  否则 `retry_stage` 这个动作同样被置 `None`：日志写的是
  `转场超时 动作=results_confirm 期望页面=通关提示/额外奖励/下一关入口 当前已确认页面=无法前往下一关`，
  看上去像「点了没反应」，实际是契约漏了一个落点。
  ⇒ **分诊口诀**：见到 `转场超时` + `当前已确认页面=X`，先查上一个动作的
  `target_pages` 有没有 `X`。没有 ⇒ 补声明；有 ⇒ 才是真的没转场。
- **战斗监督那一侧的名单（`observe_battle` 的 `result_visible`）配齐了吗？**
  这一侧最容易漏，因为它是与状态机**并列的第二个消费方**：状态机认得某一页，
  **不等于**监督认得。新路线只要有一页是「只有它自己的模板才认得出」的
  （战斗关 CLEAR、月塔三选一装置页都是这种），就必须**同时**接进监督的名单 ——
  否则监督不放行、控制权交不回状态机，表现为「45 秒静默干等 +
  `battle_unrecognized`」，而**日志里一条动作都没有**（跟上面那条的区别是：
  那条有「转场超时」字样，这条只有「安全停止」）。
  查法：把这一页的夹具丢给 `observe_battle`，那五项判据必须有一项为真；
  范本见 `tests/test_epic7_side_story.py::SideStoryBattleObservationTests`
  （含「真实战斗画面不得被判成战斗结束」的反向护栏）。
  ⚠️ **接进名单只是第一步，还要验「那把尺子在这一帧上量得准不准」。**
  2026-10-15 支线故事第三次实跑就死在这里：名单接对了，但那个模板裁的是横幅的
  **发光动画区**、走**原样 RGB** 口径 ⇒ 同一屏不同帧在 0.9115~1.0000 之间漂，
  阈值 0.92 夹在中间 ⇒ 补判跑了、结论却是 False，监督照旧干等 45 秒。
  所以「判据在这一帧上不是 `None`」这种写法**查不出**这类错 —— 必须把分数与
  余量一起断言。
- **这条判据的模板与口径选对了吗？（会变的底图 / 动画 = 判据是间歇的）**
  判据间歇失效的根因通常是模板里装了**会变的内容**：场景底图（换关卡就换）、
  动画（脉冲的发光、伸缩的装饰线）。原样 RGB 比（`TM_CCOEFF_NORMED`）会把
  底图算进相似度，于是同一台机器上同一页的分数能漂 0.09 以上，阈值被夹在中间。
  两条自查：
  1. **模板该裁哪一块？** 裁「语义标识」（文字 / 图标本身），不要裁「发光 /
     光效 / 背景」。支线故事的战斗关 CLEAR 就是实例：裁发光区时真 CLEAR 与
     **剧情关 CLEAR** 只差 0.044（分不开），裁到「CLEAR 字标带」+ 白掩膜口径
     之后差 **0.77**（`tests/test_epic7_side_story.py::SideStoryClearRulerTests`）。
  2. **该走哪个口径？** 白底控件（右上角那排图标、纯白文字）用
     `core.matcher.MATCH_MODE_WHITE_MASK`（两侧先二值化成「哪些像素是白的」再比），
     它把底图与光效一起抹平。月塔 `auto_off` 与支线 `battle_clear` 都走这一档。
     ⚠️ 换口径**必须同时重定阈值**（两个口径的分数不在同一个量纲上），并且
     下面三件事一起看：`tests/test_epic7_tower.py` 里那几条（真阳性余量、
     真实战斗帧的地板、非目标页的天花板）。
- **这条点击判据能不能「证伪」？还是只在「像不像」这一层打分？**
  「像不像」永远不是唯一性。判据必须能把**外观同类、语义不同**的对象**排除掉**，
  而不是把它们压到一个稍低的分数上。自查一句：**还有别的东西长得跟它一样吗？判据
  靠哪一维把那些东西分开的？** 答不出第二问，就还没到「可点」这一层。
  - 2026-10-18 社区签到：判据是「白底 + 有字 + 不是图片」，而**作者名行**同样满足
    ⇒ 点下去打开**作者账号主页**（没登记过的页面）⇒ 卡死 150 秒。补的那一维是
    **这一行字的横向跨度**（作者名 251px、正文 569~842px，中间 400~549 **一条都没有**）
    ⇒ `pages.feed_tap_band_is_post_body`（护栏 `FeedPostTapRulerTests`）。
  - 反例（不许的做法）：把某一条阈值从 0.03 调到 0.10，让作者行「刚好」落在下面。
    那不是唯一性，只是把概率改小了 —— 下一次滚一屏又回来了。
  - 同一条道理也适用于**判页**：一个锚点如果「本页有、邻页也有」（共享控件），
    它不是判据，只是**线索**。往判据表里加之前先问「它在该页专有吗」。
- **未登记的页面出现时，这条路会怎样？**
  ⚠️ 这是本条清单里**最容易被忽略、代价最大**的一问：H5 / 网页型页面的页面集是
  **开放的**（账号主页、话题页、转发页、举报页…），补判据永远追不完。
  所以先看**它落到一个从没见过的页面上时会发生什么**：
  - ❌ 「抛认不出 ⇒ 等状态超时（几十到 150 秒）⇒ 整条路线失败」= 把一次点歪
    放大成全路线故障，而且**超时窗口里通常一行日志都没有**，事后无从查起。
  - ✅ 「先退出去，再回到已知页」（`community` 的 `RECOVERING` + 三级逃生门是范本：
    返回键 ×2 → 左上角箭头，**按一次判一次**、**先等两帧确认**、**有界**）。
  两条硬要求：① 逃生动作**必须有界**（连按返回会把整个 H5 退掉，比原来的错更贵）；
  ② 退回已知页之后要把**刚才那一步退回来重做**，否则一次点歪 = 一轮白做。
- **认不出的那一刻，日志里留下了什么？**
  只写「认不出」等于没写。必须留下**能分辨原因的**东西：
  - 每个判据的**真实分数**（不是空列表），至少 Top3；
  - **认不出当时**的那一帧（不是超时之后那一帧）；
  - 一行心跳（每 10 秒），否则长时间的 `sleep + continue` 会是**一片空白**。
  ⚠️ 2026-10-18 之前社区签到的写法是 `PageJudgement("unknown", 0.0, ...)` ——
  那个 `0.0` 是**写死的**，`observations` 在 unknown 时必然是空列表 ⇒ 11 天 15 次
  失败的日志**字字相同**（`最高分 0.0000；已知观察=[]`）⇒ 每次修都只能猜。
  现在改成 `PageJudgement.scores`（同一趟匹配顺带留下全部分数，不多跑）。
- 超时诊断能否回答“点击前是什么、点击后变了哪里、为什么没确认”？
- 轮次是否只在完整业务闭环后增加？

## 新路线准入（强制）

新路线从第一天起必须过**两道关**：每个动作「长眼睛」（本节）+ 开局能接力（见下文
「接力契约」）。两道关**都是代码级强制** —— 漏了在 **import 阶段**就报错，
不靠人记、也不靠 code review 抓。

动作的判据分两种，每个动作**必须声明其中一种**：

1. **换页动作** —— 声明 `source_page`（从哪来）+ `target_pages`（允许到哪去）；
   主循环在点完之后会等目标页出现，等不到就按额度重试并在超时后失败关闭。
2. **不换页动作**（点开关、勾筛选、原地领奖……）—— 声明 `source_page` + `in_page_evidence`
   （靠页面内的什么变化来验收，例如“自动按钮由橙变蓝”“原槽位不再有可操作购买按钮”）。
   ⚠️ **不换页的动作不要声明 `target_pages=(本页,)`**：本页永远在集合里 ⇒ 验收永远通过 ⇒
   等于没长眼睛，分不出“点了没生效”和“点了生效了”。

### 机器校验

**每条路线都必须表态**，二选一 —— 打开开关、或进豁免名单写明「用自己的什么机制验收」。

**表态 1：打开开关**（继承 `ModeRunnerBase` 的路线）

```python
class NewRouteRunner(ModeRunnerBase):
    _REQUIRE_TRANSITION_CONTRACT = True   # 默认 False，老路线行为不变
```

打开后，主循环在发出动作前逐个校验：缺 `source_page`，或 `target_pages` 与 `in_page_evidence`
**两者皆空**，直接抛错停止——**空跑也会拦**，不会等到实跑才暴露。

**表态 2：进豁免名单**（`games/epic7/modes.py::TRANSITION_EXEMPT`）

写明「用自己的什么机制验收」，例如竞技场用 `source_state` / `target_states` 且缺合同直接 `raise`、
刷书签用自己的 `_wait_stable`。⚠️ 名单里标着**已知欠债**的条目（`survivor` / `fodder`）
是真缺判据，不是「用了别的机制」—— 写在那里是为了让缺口在明处。

`hero_synthesis` 曾经也在这份欠债名单里，**2026-10-03 移出**：那 3 个缺契约的动作补齐后，
它的每个动作都带 `source_page` ＋ `target_pages`。它一度留在豁免名单里，理由是
「判据齐全、开关尚未打开」＋「页内证据字段名 `source_observation` 与机器认的
`in_page_evidence` 还没对齐」——**性质不同**，不是欠债。

✅ **2026-10-04 已从豁免名单整条删除**（第五个打开机器强制的路线，继
`knights_donation` / `world_boss` / `sanctuary` / `labyrinth_stone` 之后）：
先做**字段名对齐**（`HeroAction.source_observation` 删除，改用基类 `RouteAction.in_page_evidence`，
全文件 34 处 + 测试 33 处 + `runner_base` 2 处），再打开 `_REQUIRE_TRANSITION_CONTRACT = True`。

⚠️ **为什么要先对齐字段名 —— 不对齐时开关「开着也管不到」那 12 个同页动作**：
开关读的是基类的 `in_page_evidence`，而英雄合成当时用的是自造名 `source_observation`。
名字不齐时，12 个 `material_change` 同页动作只能靠 `target_pages=("刻印加材料", "刻印SSS材料")`

这条给出一个通用检查动作：**打开某条路线的开关之前，先跑一遍那个检查函数，别只看字段填没填**
——尤其要确认「路线自造的证据字段名」和「开关读的字段名」是不是同一个。`world_boss`

| 关 | 在哪 | 漏了会怎样 |
| --- | --- | --- |
| 加载期自查 | `modes._assert_transition_stance_declared()`，import 时执行 | **报错，程序起不来** |
| 护栏测试 | `tests/test_transition_contracts.py::TransitionStanceTests` | 自查被人删掉时兜住 |

⚠️ **开关只对继承 `ModeRunnerBase` 的路线有意义**。`shop_refresh` / `survivor` 是
自带独立主循环的裸定义，那段校验它们**走不到**；`arena` / `expedition` 继承的是

所以别看到「它的动作没有 `target_pages`」就推断「打开开关会抛错」，

`in_page_evidence` 目前是**声明性字段**：机器能校验“填了没有”，不能校验“填得对不对”。
所以填它的同时，仍要按上面契约模板的字段说明把证据写清楚，别拿一句“页面变了”敷衍。

⚠️ **别把 `target_pages=(本页,)` 当成 `in_page_evidence` 的替代品**，也别为了保证“能验收”而

## 接力契约（路线准入的另一半）

**转场契约**管的是「跑起来之后，每个动作长没长眼睛」；
**接力契约**管的是「开局时人停在半路，能不能从那一步接上」。

这两件事**互相独立**：一条路线的动作可以个个都长眼睛，却完全不支持接力（人一停到半路，
助手照样退回大厅从头走）。反过来，接力的判断也可以很准，而动作本身没有出口验收。
**所以两个契约要分别立规矩，不能拿一个当另一个的替代品。**

### 为什么不能照抄转场契约的卡法

转场契约是**逐个动作**校验的：主循环每发出一个动作之前查一次，漏写当场抛错。
接力是**开局一次性**的：整条路线只在启动那一刻问一句「你现在停在哪一页」，
没有「动作」可查、也没有第二遍机会。

所以「接力必须在代码上卡住」的等效卡点是**三处**，缺一处都还能悄悄漏掉：

| 卡点 | 卡的是什么 | 漏了会怎样 |
|---|---|---|
| **① 表上必须表态** | 有导航的路线，要么挂接力判断，要么写明「不做接力，因为……」 | 写新路线时**一个字不提接力**也能跑通，没人发现 |
| **② 接线必须真通** | 启动时回头查一句「那个判断到底被执行过没有」 | 判断写了、启动流程忘了调：**表面一切正常**，人停半路照样退回大厅 |
| **③ 判据必须真认得准** | 拿该路线的全部夹具跑一遍，覆盖率登记在案 | 判断本身认错别人的画面（本项目已实测到：见下） |

### ① 表上必须表态

`games/epic7/modes.py` 的 `RESUME_EXEMPT` 是**豁免名单**：只有写明理由的路线才允许没有接力判断。
`MODE_SPECS` 在模块加载时自查，冲突直接抛错 —— **import 都过不去，更不用说启动**。

`needs_navigation=False` 的路线（起点本来就是人工推进到活动内部再启动）**自动豁免**，
不需要进名单。其余路线要么挂 `resume_probe`，要么进名单。

### ② 接线必须真通

`main.py::_enter_mode` 在走完接力路径后检查 `_ResumeWatch.asked`：探针**必须被真的问过至少一帧**。
只查「探针存不存在」是不够的 —— 存不存在是静态的，接线通不通只有跑一遍才知道。

### ③ 判据必须真认得准

**光看代码判断不出判据准不准。** 本项目实测到的例子：骑士团捐赠「获得奖励」那一页的判据，
在 `epic7_hero/reward_popup.png` 与 `epic7_story/bonus_reward.png` 上**同样成立** ——
别的路线的弹窗能骗过它。这种毛病读代码看不出来，只有拿全库夹具跑一遍才现形。

所以要求：
- **跨路线负例扫描**（全库夹具取最高分）必须有，结论写进 `docs/RESUME_COVERAGE.md`；
- **本路线夹具全认出**做成自动测试（`tests/test_resume_contracts.py`），进门槛。

### 什么算「可停靠环节」

「环节」= 人**可能手动停住**、且**停在那里是有意义的**画面。下面三类不算：

1. **弹窗不接力。** 不是「来不及做」，而是**不需要**：返回大厅那一下 Back 会先关掉弹窗
   （等于取消），下一帧人就落在底页上，探针在那一刻就地接管 —— 效果一样，还更安全。
   所以别为弹窗单独建判据。
2. **不可逆动作的页面不接力。** 点下去就消耗掉资源的那些（买票、购买确认、花掉每日额度……）：
   接力到这一页等于**助手替你按下不可逆的确认**。`arena` 的买票弹窗压住的队伍页就是这么
   用 `no_ticket` 显式排除的。
3. **终态不接力。** 已经跑完、没有下一步的画面。

### 写一条路线的接力，要动这些地方

| 文件 | 加什么 |
|---|---|
| `<路线>.py` | `detect_resume_point(machine, screen, ...)` + `resume_from(...)`（要拨状态时） |
| `modes.py` | 在 `MODE_SPECS` 里挂 `resume_probe=_resume_probe(<本路线的 detect_resume_point>, ...)` —— **探针本体不用手写**，工厂会把「认落点 → 拨状态 → 回填」做掉 |
| `modes.py` | 落点在**导航链上**时，把那一页写进该路线 `navigation_plan.resume_entries`（**链条本身也在同一个 `NavigationPlan` 里声明**）。⚠️ 不需要动 `navigation.py` —— 那是执行器、只认数据；`navigation._RESUME_ENTRY_PAGES` 是由计划派生的只读视图 |
| `tests/test_<路线>_resume.py` | 落点矩阵 + 探针接线 + 「停在非本路线页面上必须返回 None」 |
| `docs/RESUME_COVERAGE.md` | 登记这条路线**每个**环节的接力状况（能/不能 + 为什么） |

（`detect_resume_point` 的签名各路线略有差别 —— 主线/远征/竞技场要看导航器认出来的页面名，
所以多一个 `observed_page` 参数；世界首领战/骑士团捐赠/刷书签只用状态机自己的判据，用不到。
**由 `modes.py` 的探针去适配**，对外统一成 `(machine, screen, navigator)`。）

⚠️ **落点顺序即优先级**，顺序表必须自带注释写清「为什么这么排」——
两个锚点在同一页上都可见时，顺序错了会把已选好的状态退回重来。

⚠️ **把某页从「不接力」改成「接力」时，先 grep 反向断言**：既有测试里可能有
`assertIsNone(...)` 或「接力反面名单」（`for name in (...)` + `assertIsNone`），
只 grep 正向断言会漏掉它们。
