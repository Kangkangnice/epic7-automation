# 视觉证据集中化与界面改版维护设计

## 背景

项目当前已经具备状态机、有限重试、两帧稳定、全局弹窗守卫、失败截图和固定样本测试。英雄合成、竞技场、远征和主线已经作为模拟器正式功能使用。

当前主要维护成本来自视觉配置散落在各路线实现中：模板路径、搜索区域、匹配阈值、页面组合和点击依据常与业务判断写在同一文件。E7 只改变外观或按钮位置时，维护者仍需阅读状态机才能找到修改点，也难以从一次失败诊断直接知道哪个证据失效。

## 目标

普通 UI 改版时，维护者只替换模板并修改少量视觉证据配置，不修改业务状态机；诊断必须明确指出在哪里改、改什么以及为什么失败。

可验证的最终结果：

1. 旧模板在新版完整截图上稳定失败，并留下明确诊断；
2. 诊断列出证据名称、配置文件、模板文件、搜索区域、匹配分数和阈值；
3. 维护者只替换模板或修改证据配置；
4. 业务状态机保持不变；
5. 正例、反例、转场回放和路线闭环测试重新通过；
6. 模拟器实机一轮通过后才声明完成。

## 范围

本轮只处理模拟器视觉证据的维护基础设施，并按以下顺序迁移：

1. 竞技场样板；
2. 主线；
3. 远征；
4. 英雄合成；
5. 最后评估狗粮和助手自动实验路线。

本轮不处理 PC 后端、任务队列、在线更新、完整 YAML/JSON 工作流、自动降低阈值、自动覆盖模板，也不同时拆分英雄合成业务文件或重写全部 Runner。

## 架构边界

数据流固定为：

```text
视觉证据层
  → 回答当前页面、控件位置和量化分数
业务状态机
  → 根据页面和业务上下文选择唯一动作
转场执行层
  → 点击、确认来源退出、确认目标进入、有限重试或安全停止
```

新增 `games/epic7/evidence/`，每条路线维护自己的证据清单：

```text
games/epic7/evidence/
├─ common.py
├─ arena.py
├─ story.py
├─ expedition.py
└─ hero_synthesis.py
```

`common.py` 只提供当前四条正式路线确实共用的少量数据结构和校验，不承载游戏业务。不得建立一个包含所有路线的巨大注册表。

每个原子证据至少声明：

- 稳定键名；
- 模板路径；
- 基准分辨率下的搜索区域；
- 匹配阈值；
- 识别方式；
- 点击使用模板中心还是明确的基准坐标；
- 对应正例和反例 fixture；
- 人类可读的用途说明。

每个页面证据至少声明：

- 页面稳定键名；
- 必须同时成立的原子证据；
- 可任选其一的证据组；
- 出现时导致 `UNKNOWN` 的冲突证据；
- 默认稳定帧数；
- 维护文件位置。

复杂业务继续保留在 Python 状态机中。例如 SSS 优先级、同名相邻副本、资源安全、是否允许购买、难度选择和循环完成都不是视觉配置。

## 转场表达

各路线可以保留现有 Runner，但改变页面或业务状态的动作统一表达以下字段：

- 动作名称；
- 来源页面；
- 允许目标页面；
- 动作是否可逆；
- 来源仍在时的重试额度；
- 来源消失后是否只能等待；
- 业务成功证据；
- 失败诊断要求。

本轮先统一字段、日志和测试语义，不强制竞技场、远征和英雄合成共用一个事务执行器。只有至少两条路线出现经过测试证明的重复实现后，才评估进一步抽取。

## 诊断包

证据或转场失败时，保存一个自包含目录：

```text
runtime_diagnostics/<mode>/<timestamp>_<action>/
├─ screen.png
├─ source.png
├─ target.png
└─ evidence.json
```

`evidence.json` 至少记录：

- 模式、轮次、动作和尝试次数；
- 预期来源和允许目标；
- 来源是否仍成立；
- 各关键证据的模板、配置文件、区域、分数和阈值；
- 冲突证据；
- 原事务目标；
- 最终结论：来源仍在、转场中、目标已进入或 `UNKNOWN`。

诊断必须区分“模板未匹配”“匹配发生在搜索区外”“证据冲突”“来源未退出”“目标未进入”和“业务结果未确认”，不能统一写成超时。

## 维护检查命令

提供只读检查工具：

```text
python tools/check_evidence.py --mode arena --screen <完整截图>
```

输出该路线全部相关证据的名称、模板、配置位置、分数、阈值、匹配位置和页面判定。工具不得自动修改模板、区域或阈值。

## 标准维护流程

1. 查看诊断包，先判断是视觉外观变化还是业务流程变化；
2. 外观变化只替换模板，必要时调整证据区域或阈值；
3. 把当前完整截图加入 `tests/fixtures`，保留失败现场；
4. 运行证据正反例测试；
5. 运行页面组合和转场回放测试；
6. 运行该路线闭环测试和全量测试；
7. 干跑确认第一步；
8. 实机完整运行一轮；
9. 更新最后实机验证日期和支持记录。

只有游戏页面顺序、业务规则或循环完成条件改变时才修改状态机。

## 测试层级

每条迁移路线必须覆盖：

1. 原子证据：正例命中、近似反例不命中；
2. 页面组合：必需、任选和冲突证据的三态判定；
3. 转场回放：来源仍在时有限重试，来源消失后不重复旧动作，目标稳定后提交；
4. 路线闭环：只有业务完成并重新出现稳定入口时增加轮次；
5. 配置校验：模板存在、阈值合法、区域未越界、引用键存在、高风险动作具备来源证据；
6. 诊断测试：失败包包含约定字段和裁剪，不把 `UNKNOWN` 写成成功。

迁移必须保持原有行为，先用现有测试锁定基线。每条路线独立完成、验证和提交，不允许四条路线同时修改后一次验收。

## 迁移顺序

### 第一批：竞技场样板

迁移竞技场模板路径、区域、阈值和页面组合；增加配置校验、证据检查命令、诊断最小集和维护说明。用一次人为失效模板验证诊断能够准确指向维护入口。

### 第二批：主线

验证证据层能够表达连续页面、可选弹窗、快速/普通战斗切换和结算入口，不改变现有主线状态机顺序。

### 第三批：远征

验证难度选择、队伍、战斗、招募和返回主页等事务页面。难度三是否已选中仍由业务状态机决策。

### 第四批：英雄合成

只迁移纯视觉证据。SSS 安全、相邻同名副本、动态切换和传送事务保持原实现。视觉迁移稳定后再单独评估文件拆分。

### 第五批：实验路线

最后迁移狗粮和助手自动，并补齐缺少的转场契约。迁移不等于升级为正式功能。

## 新路线扩展

证据结构在前三条正式路线验证稳定后，新增路线按固定顺序开发：

```text
手动走完整流程
→ 写页面转场契约
→ 保存完整截图
→ 建立路线证据清单
→ 写证据正反例测试
→ 写业务状态机
→ 写转场和闭环回放
→ 干跑
→ 实机完整验收
```

不建立代码生成器。扩展指南提供一个最小示例和检查清单即可。

## 文档与单一事实来源

- 模板路径、区域和阈值只存在于证据清单；
- 维护文档只描述修改入口和流程，不复制具体数值；
- 每条证据清单记录证据版本、基准分辨率、最后实机验证日期和支持环境；
- README 只声明经过证据矩阵验收的正式支持范围；
- 任何实机结论必须有完整闭环日志或诊断记录。

## 非目标

- 不把业务状态机配置化；
- 不自动放宽阈值或接受未知页面；
- 不因为存在模板就声明支持；
- 不把视觉迁移和业务重构混在同一个提交；
- 不清理与本设计无关的旧代码；
- 不在本轮处理 PC 模板和客户端差异。

## 最终验收

最后验收由主 Agent 执行：

1. 检查每批提交只包含计划范围；
2. 检查状态机业务差异为空或有明确理由；
3. 运行配置校验、专项测试、全量测试和 Python 编译检查；
4. 使用旧版与新版 fixture 运行证据检查命令；
5. 检查诊断包能否仅凭内容定位失效证据；
6. 涉及真实游戏时，由用户完成整条路线实机闭环后才给出最终通过结论。
