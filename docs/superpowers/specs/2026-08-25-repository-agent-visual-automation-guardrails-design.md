# 仓库级视觉自动化 Agent 硬约束设计

## 背景

项目已经在 `docs/TRANSITION_CONTRACTS.md`、`docs/EXTENDING.md` 和
`docs/HUMAN_AI_WORKFLOW.md` 中记录了“点击不等于成功”、进入与退出标志、失败关闭和
实机证据优先等原则。但仓库根目录没有 `AGENTS.md`，后续 Agent 不一定主动阅读这些
普通文档，也就可能在局部修复中只实现部分契约。

本次英雄装备页切换暴露了这个缺口：实现已经要求识别英雄信息页才完成导航，却仍用
一次性布尔标志阻止点击未生效后的重试，而且导航坐标没有用当前实机证据复核。目标页
确认存在，但来源页退出、来源持续时重试和坐标证据没有形成完整闭环。

## 目标

1. 让所有进入本仓库的 Agent 默认获得同一套视觉自动化方法论。
2. 让每个改变页面或业务状态的动作都有可检查、可测试、可证伪的完整契约。
3. 防止原则只存在于文档中，却没有落实到代码、日志、测试和实机验收。
4. 让规则同时适用于现有六条路线、模拟器后端和后续 PC 端迁移。

## 非目标

- 本设计不立即抽象新的公共状态机框架。
- 本设计不顺便审计或重构所有路线。
- 本设计不改变用户操作模拟器、AI 只读观测的权限边界。
- 本设计不把实验路线改称正式支持。

## 方案选择

采用三层约束，避免只写普通文档或把所有细节堆进一个 Agent 文件。

### 第一层：仓库根 `AGENTS.md`

`AGENTS.md` 是简短、强制、默认必读的执行规则。它只保留不可违反的原则、编码前检查、
完成定义和必须阅读的详细文档链接，不复制大段路线说明。

### 第二层：详细转场契约

`docs/TRANSITION_CONTRACTS.md` 继续作为字段定义、日志语义和路线示例的唯一详细来源。
本次补充“来源持续、来源退出、目标进入”三种观测对应的重试规则，避免 Agent 只实现
目标页确认。

### 第三层：测试和日志门禁

原则必须能由测试和运行证据验证。每次修复真实故障时，先保存现场并增加失败回归；
日志断言要区分候选点击、来源未退出、转场中、目标已进入和业务已完成。

## 强制动作模型

任何会改变游戏页面、选择对象、消耗资源或推进业务状态的动作都必须明确以下五个阶段：

```text
来源页进入标志
→ 执行候选动作
→ 来源页退出标志
→ 目标页进入标志
→ 业务完成标志
```

五个阶段不能互相替代：

- 点击只证明动作已经尝试。
- 来源页退出只证明页面开始变化。
- 目标页进入只证明转场完成。
- 业务完成必须由业务结果单独证明。

对同页对象切换等没有传统“换页”的动作，来源退出可以定义为旧选择状态消失或出现
受控的切换阶段；动态立绘本身不能单独证明目标对象已经切换。

## 观测与重试规则

点击后必须继续观察，并按当前画面决定下一步：

1. **来源页仍连续稳定存在**：点击没有生效。记录来源证据和尝试次数，在额度内重试。
2. **来源页已经消失，目标页尚未稳定**：正在转场。只等待，禁止在旧坐标重复点击。
3. **目标页连续稳定出现**：记录来源已退出和目标已进入，转场才算成功。
4. **来源与目标证据冲突或都无法确认**：进入 `UNKNOWN`，保存诊断并按契约安全停止或
   执行明确限定的恢复，不把未知当作成功。

可逆导航点击可以在来源页仍成立时重试。传送、确认消耗等不可逆动作在来源页消失后
不得重试，因为动作可能已经执行但回执尚未识别。

禁止使用一次性“已点击”标志永久阻止合理重试。若需要防抖，标志必须与当前视觉状态、
尝试额度和原事务目标共同管理，并在来源页仍稳定时允许下一次受控尝试。

## 坐标与视觉证据

- 固定坐标必须由当前客户端完整截图或已标定布局证明落在目标控件内部。
- 同一控件在不同模块出现两个坐标常量时，修改前必须用实机 fixture 复核，不能任选其一。
- 模板匹配必须限定搜索区域；动态背景、呼吸动画和粒子区域不得作为唯一状态证据。
- 阈值、像素数或匹配分数参与决策时，日志和回归测试必须能够显示或断言关键数值。

## 日志要求

每个转场至少能从日志回答以下问题：

- 点击前识别到了哪个来源页，依据是什么？
- 点击了哪个动作、哪个坐标、当前第几次、最多几次？
- 点击后来源页是否仍存在？若重试，为什么？
- 来源页何时确认退出？
- 目标页何时稳定进入，依据和连续帧数是什么？
- 业务何时真正完成，依据是什么？
- 失败时原事务目标、最后观测和诊断文件在哪里？

在目标证据出现前，日志禁止使用“导航完成”“转场成功”或“业务成功”。未确认必须明确
写为未确认，不能让成功日志与实际画面相矛盾。

## 开发与修复流程

修改视觉行为前必须：

1. 用日志、当前截图或固定 fixture 证明问题，不凭推测直接修改。
2. 写明来源进入、来源退出、目标进入、业务完成、重试和 `UNKNOWN` 条件。
3. 将真实失败现场加入 fixture，并先写能稳定复现的失败测试。
4. 只实现通过当前契约所需的最少代码。
5. 运行专项测试、全量测试和编译检查。
6. 涉及实机画面时，由用户完成完整业务闭环实测；局部走过若干英雄或页面不能代替完整
   流程验收。

没有完整闭环证据时，Agent 只能报告“离线验证通过”或“等待实机验收”，不能宣称流程
已经修复或正式可用。

## 当前英雄信息页问题的应用

后续实现必须把英雄装备页切换修正为以下契约：

- 来源进入：英雄列表容器稳定，且装备标签连续稳定选中。
- 候选动作：点击经 fixture 验证的英雄信息标签内部坐标。
- 来源退出：装备标签不再选中；若装备标签仍稳定选中，则记录点击未生效并重试。
- 转场等待：装备标签已经消失但信息标签尚未稳定时不重复点击。
- 目标进入：信息标签连续稳定选中后才允许继续筛选和英雄合成导航。
- 失败：达到重试额度仍未退出装备页，或观测冲突，保存带关键像素数和尝试次数的诊断并
  安全停止。

测试必须覆盖首次点击被吞、第二次点击生效的回放，且日志能够证明第一次为什么不算成功。

## 完成标准

本项实施完成需同时满足：

1. 仓库根存在简明的 `AGENTS.md`，并链接详细契约和协作手册。
2. `TRANSITION_CONTRACTS.md` 明确来源持续、来源退出、目标进入和不可逆动作的差异化重试。
3. 当前英雄装备页切换具有首次点击未生效的失败回归测试。
4. 实现使用实证坐标，并在来源仍存在时按额度重试。
5. 日志明确输出进入、退出、目标到达、关键数值和尝试次数。
6. 专项测试、全量测试和编译检查通过。
7. 用户完成一次从装备子页启动到英雄合成完整一轮的实机验收；在此之前只标记为等待
   实机验收。
