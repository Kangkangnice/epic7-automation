# 狗粮模式设计

## 目标与边界

新增命令行模式 `fodder`，用户可把它称为“狗粮”。目标关卡固定为“特别的时间之书”中的 Episode 3-7，不增加关卡选择参数，也不改动主线、竞技场或远征现有流程。

实跑命令沿用统一接口：

```powershell
python -u -m auto_game_unified.main --mode fodder --max-cycles N --live --confirm RUN
```

## 已确认的当前客户端流程

入口链路来自 2026-08-14 实机截图：

```text
大厅 → 支线故事 → 特别的时间之书 → Episode
→ 冒险 → 已选中的 3-7 → 准备战斗
→ 选择辅助英雄 → 选择队伍 → 战斗开始
```

首次进入当前客户端时，Episode 后存在“冒险”页；导航必须逐页确认，也允许客户端记住进度后直接出现后续页面。

循环链路为：

```text
战斗 → CLEAR → 点击安全区域 → 结算确认
→ 重新进行 → 选择辅助英雄 → 选择队伍 → 战斗开始
```

只有“重新进行”稳定出现时才把上一轮计为完成。达到目标轮数后停在该页面，不再点击“重新进行”。

## 分层实现

- `navigation.py` 只负责从大厅进入狗粮模式的首个业务页面，并识别新增入口页面用于受控返回大厅。
- `fodder.py` 定义狗粮页面状态、模板、纯视觉动作决策和循环 Runner。
- 战斗阶段复用 `BattleSupervisor`、共享自动战斗控件识别和 `RecoveryGate`。点击“战斗开始”后立即锁定恢复；识别到 CLEAR/结算以前禁止返回或 Back。
- 体力不足复用主线当前客户端的生命之叶三锚点校验。只允许选择生命之叶和确认，永不点击天空石；生命之叶不可用或补充失败时以资源耗尽安全结束。
- 网络异常继续由全局截图守卫处理，P 键、日志、当前帧和失败诊断继续使用通用 Runtime。

## 识别与安全规则

每个页面使用限定区域内的稳定文字或图标模板；不以角色、章节背景或动态体力数字作为锚点。普通动作要求连续两帧一致，点击后必须看到后继页面；同一动作最多两次。

允许的循环业务按钮只有：CLEAR 安全区域、结算确认、重新进行、选择队伍、战斗开始，以及经过标题/材料/确认三重校验的生命之叶补充。未知页面保存诊断并停止，不盲点。

## 验收

- 入口与循环的完整实机截图成为离线 fixture。
- 离线测试覆盖入口顺序、两轮计数、目标轮数不再重开、生命之叶补充/耗尽、黑屏与未知页、战斗恢复锁和 CLI 注册。
- 专项与全量离线测试通过后，实机只走一轮最小验收；不在未监控状态下启动长循环。
