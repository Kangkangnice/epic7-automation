# PC 英雄合成迁移：单步证据化验证设计

**日期：** 2026-08-20
**状态：** 已确认方案，待用户复核后执行

## 背景与结论

英雄合成的现有状态机和离线测试以模拟器画面为依据。`templates_pc/hero` 虽然存在文件，但其中至少“灰色刻印按钮”和“SSS 评级”是整屏截图，不能作为 PC 客户端的稳定匹配锚点；现有英雄合成流程测试也没有使用 PC 画面。因此它不视为已迁移。

本次不重写业务逻辑，也不先实现抽象的通用探索引擎。以现有 `HeroSynthStateMachine` 为骨架，为 PC 客户端逐页采集证据、建立局部模板、修复被实测否定的判断或点击点，并以一次真实闭环证明可用。

## 授权与范围

用户已授权在本次验证中：

- 实际消耗英雄材料并点击合成确认；
- 在实际出现且识别可靠时执行传送流程；
- 由自动化负责截图、定位、单步点击及每步后的页面验证。

不在本次范围：

- 竞技场路线和其门票验证；
- 对其他路线的代码重构；
- 付费货币购买或用户未明确出现的资源兑换；
- 为一次性流程设计独立的通用框架。

## 路线与页面模型

主流程按以下顺序采集和验证：

```
大厅
  → 英雄列表
  → 筛选面板（确认 3 星）
  → 英雄详情卡（本轮默认非 SSS）
       ├─ 无红点：下一张
       └─ 有红点：刻印材料页
                       → 逐张加入 Up 材料
                       → 合成按钮
                       → 合成确认弹窗
                       → 返回英雄列表
  → 列表结束
```

本账号当前尚未出现 SSS 英雄。因此，SSS 评级识别、SSS+红点的跳过逻辑与
传送分支均不作为本轮 PC 验收条件，待实景出现后再单独采集、测试和启用。

若后续实景触发传送页面，作为独立后续分支验证：

```
传送选择 → 选卡 → 传送确认 → 奖励页关闭 → 英雄列表
```

传送不因“代码存在”而假定已可用；必须有完整的 PC 页面证据才点击下一步。

## 单步证据协议

对每一个页面动作都执行相同的门槛：

1. 截图当前稳定画面，存为 PC 夹具；记录页面名、动作名、模板分数和候选坐标。
2. 模板只截取固定视觉元素或按钮文本，避开英雄名、数量、战力、材料计数、动态动画与整屏背景。
3. 校验坐标位于该按钮的安全热区后，执行一次点击。
4. 等待稳定，截图点击后画面；确认它属于预期下一页集合，而非仅确认“画面发生变化”。
5. 失败、低置信度、未知页或预期外弹窗时，保存诊断并停止；不做盲点和重复消耗操作。

合成和传送确认都是不可逆动作。只有确认弹窗的双锚点、点击坐标和点击后的结果页都已被单步验证，才会在真实闭环中执行。

## 最小代码策略

保留现有 `HeroSynthStateMachine` / `HeroSynthRunner` 和平台根目录选择方式。

只在实测证明必要时修改：

- `games/epic7/templates_pc/hero/`：替换为 PC 局部模板；
- `tests/fixtures/epic7_pc_hero/`：保存每个页面的前后实景夹具；
- `tests/test_pc_hero_synthesis_evidence.py`：为 PC 识别、动作坐标和状态转移加入回归测试；
- `games/epic7/hero_synthesis.py`：仅修复 PC 夹具已经复现的区域、阈值、点击点或状态判断。

不把模拟器模板复制到 PC，也不以整屏模板或单一动态截图通过测试。

## 验收条件

离线证据：

- 本轮参与 PC 决策的模板可加载且均为局部静态裁剪；其中不包括 SSS
  评级及传送专用模板；
- 每个已采集状态至少有一张正向夹具；含动态数据的关键页至少有两张变体夹具；
- 每个动作的目标坐标在按钮安全区域内，且测试断言预期动作和坐标；
- 完整 PC 夹具序列能模拟跑到一轮结束；SSS/传送分支只在后续出现实景时
  单独通过。

在线证据：

- 先完成全程单步验证，所有点击后页面均符合预期；
- 再实际运行一轮；日志和截图证明筛选、材料加入、确认、返回及完成条件均正确；
- 发生未知页面时自动停住并保留现场，不继续消耗资源。

## SOP 回写

本次结束后，把实测结果回写到 PC 迁移 SOP：新增或修订动态区域裁剪、不可逆操作双证据、点击后状态证明、UAC 输入预检和平台专属夹具等规则。只记录实际遇到且可复现的经验，不将本次临时判断泛化成无依据的框架。
