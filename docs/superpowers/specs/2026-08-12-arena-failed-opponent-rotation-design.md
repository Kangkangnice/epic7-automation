# 竞技场失败对手轮换设计

## 目标

竞技场挑战失败后不再重复选择同一名对手。每次回到对手列表，都以当前画面为准，从尚未失败的对手中随机选择；三名对手均已失败时点击右上方的免费刷新，确认新列表出现后再选择。

真实模拟器验收仍由用户执行；AI 只修改代码并运行离线测试。

## 现状与根因

当前 `ArenaStateMachine` 只实现了 `select-first-row`，每次进入列表都固定点击第一行。它既不识别失败行，也不保存当前选择，因此失败结算返回列表后会再次挑战同一个对手。

最新失败现场显示：已失败的第一行整行呈红色，另外两行保持灰色。对姓名左侧附近的背景区域做 HSV 红色占比统计，三行分别约为 `88.4%`、`0.01%`、`0%`；现有普通列表 fixture 三行均接近 `0%`。因此可以用局部背景色可靠地区分失败行，不需要 OCR，也不需要从结算画面推断胜负。

## 页面识别与动作

- 三名对手沿用当前列表布局，以 `list_ready` 锚点为基准计算三个相对点击点，避免受模拟器窗口在桌面中的位置影响。
- 每行只检查姓名左侧附近的背景区域，避开头像、英雄图标和文字。区域按当前 `1982×1132` 参考画面定义，并随窗口画面等比例缩放。
- HSV 红色像素占比高于保守阈值时，该行视为已失败；颜色不明确的行不参与点击，避免误选。
- 从所有明确未失败的行中随机选择一行。随机源允许在离线测试中注入，生产默认使用 Python 随机选择。
- 三行均明确为失败时，返回 `refresh-opponents`，点击顶部带循环箭头的“免费”刷新按钮。
- 刷新点击后必须连续识别到新列表且至少出现一名可选对手，才允许继续；刷新本身不增加完成轮数。
- 若列表存在无法明确分类的行且没有安全候选，不盲点刷新或对手，沿用超时、诊断和安全停止。

## 状态与计数

- 战斗结算确认后回到列表，仍表示完成了一次实际挑战；胜负都增加 `completed_cycles`。
- 回到列表时不再自动把状态提前改为 `SELECTED`。先根据当前截图产生 `select-opponent-N` 或 `refresh-opponents` 动作，再由 Runner 验证转场。
- 选择对手成功后进入现有 `SELECTED → TEAM → BATTLE → RESULT` 流程。
- 刷新成功后保持 `LIST`，下一次稳定观察再选择对手。
- 画面本身是失败记录的唯一事实来源，因此脚本重启、恢复导航或列表顺序变化后仍然正确；不新增持久化或进程内失败集合。

## 模板与测试

- 将最新真实失败列表保存为竞技场离线 fixture；已有普通列表作为全可选反例。
- 新增测试覆盖：只跳过红色第一行、从安全候选中随机选择、三行全红触发刷新、刷新不计数、普通列表三行均可选、颜色不明确时不盲点。
- Runner 测试覆盖确认结算后先回 `LIST`，以及刷新后继续选择而不错误等待 `SELECTED`。
- 运行竞技场专项、跨模式安全测试和全项目离线回归；不启动或控制模拟器。
