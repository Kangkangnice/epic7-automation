# 视觉证据集中化验收修复设计

## 背景

视觉证据公共结构、竞技场检查器以及竞技场、主线、远征、英雄合成四条路线的证据清单已经实现，但最终审阅发现当前实现尚未满足“配置唯一、诊断可信、运行时共用”的目标：检查器与生产状态机可能对同一截图给出不同页面结论，低于阈值的匹配分数被丢弃，英雄合成仍使用重复的区域和阈值，新的自包含诊断没有接入生产失败入口，部分证据构建器还会静默跳过缺失模板。

## 目标

本轮只修复视觉证据集中化的验收缺口，不改变游戏业务顺序、资源安全规则、点击位置、重试额度或循环完成条件。

可验证结果：

1. 竞技场官方 `selected.png` 与快速战斗队伍页在检查器和生产状态机中得到相同页面结论；
2. 原子证据未达到阈值时仍记录最高匹配分数，并输出证据配置文件、模板、区域、阈值和位置；
3. 英雄合成已迁移的区域和阈值只从证据清单读取；
4. 四条正式路线通过现有统一失败出口保存自包含证据目录；
5. 证据模板缺失时，配置校验明确指出缺失文件；
6. 新增回归测试和全量测试通过。

## 方案选择

采用“路线专用页面判定，共用同一生产入口”的方案。

- 不扩展成声明式规则语言。分数比较、快速战斗和颜色证据继续用普通 Python 表达。
- 每条路线在自己的 `games/epic7/evidence/<route>.py` 中提供页面判定函数或等价适配器。
- 检查器与生产状态机调用同一判定入口，不再分别维护页面组合逻辑。
- `PageEvidence` 继续承担简单的必需、任选和冲突组合；复杂页面由路线适配器补充。

不采用以下方案：

- 不建立分数表达式 DSL，避免为当前四条路线引入新的规则引擎。
- 不只修补检查器，因为那会继续保留两套页面判断。

## 原子证据与量化分数

`inspect_profile` 必须先取得搜索区域内的最高匹配分数，再根据 `score >= threshold` 计算 `observed`。低于阈值不是“没有分数”，而是“有分数但未通过阈值”。

每个观测结果至少包含：

- 证据键名；
- 证据配置文件；
- 模板文件；
- 搜索区域和基准分辨率；
- 原始最高分；
- 正式阈值；
- 是否通过阈值；
- 匹配位置。

检查器只读，不自动修改模板、区域或阈值。

## 页面证据共用

竞技场必须首先覆盖两个已复现差异：

- `selected.png` 中 `challenge` 与 `list_ready` 可以同时命中；生产规则以两者分数比较确认是否选中。
- 快速战斗队伍页即使没有普通 `battle_start`，只要快速战斗证据成立，仍属于有效队伍页。

检查器不得把上述有效页面报告为 `UNSAFE` 或 `UNKNOWN`。生产状态机不得在本轮改变原有判定含义，只把判定实现移动或委托给证据模块。

主线、远征和英雄合成按相同原则接入已有页面判定，不借本轮修改业务流程。不能由当前原子证据可靠表达的复杂页面保留路线专用函数，并在诊断中明确列出使用的依据。

## 英雄合成配置唯一性

英雄合成状态机从 `EvidenceProfile` 读取已迁移证据的区域与阈值。以下重复值必须由证据键替代：

- 当前英雄 `rating_sss` 的区域和阈值；
- 材料页 `sss_material` 的区域和判定阈值；
- `filter_attribute_label`、`filter_star3_unselected` 等已进入证据清单的阈值；
- 合成、警告和传送结果模板的已迁移区域。

SSS 优先级、材料安全三态、相邻同名副本和不可逆传送事务仍留在业务状态机中。

## 缺失模板校验

证据清单必须声明预期模板，即使文件当前不存在。构建器不得因为 `Path.is_file()` 为假而删除原子证据。可选模板通过显式的 `optional` 元数据或最小等价结构表达；必需模板缺失必须产生“模板不存在”错误。

本轮只增加当前路线实际需要的最小可选语义，不建立通用资产管理系统。

## 生产诊断接入

复用现有 Runner 的统一超时和未知页面出口，向 `write_evidence_diagnostic` 传递模式、动作、来源、允许目标、尝试次数和最后一帧证据。只有无法通过公共出口覆盖的路线才增加最小路线适配。

诊断目录必须包含：

```text
screen.png
source.png（有来源区域时）
target.png（有目标区域时）
evidence.json
```

诊断失败本身不得覆盖原始业务异常；写入异常只追加日志并保留原有安全停止行为。

## 测试策略

严格按回归测试先行：

1. 用现有 `selected.png` 证明检查器与生产状态机当前结论不一致；
2. 用快速战斗 fixture 证明队伍页当前被检查器判成 `UNKNOWN`；
3. 构造低于阈值的模板匹配，断言仍有数值分数；
4. 修改测试 profile 的英雄阈值和区域，证明状态机确实读取 profile；
5. 用临时空模板目录证明必需模板产生“模板不存在”；
6. 触发统一失败出口，断言自包含诊断文件存在且字段完整；
7. 运行视觉证据专项测试、四条路线专项测试和全量测试。

每个测试必须先在现有实现上出现预期失败，再写最小生产改动。

## 提交与工作区约束

- 不重写已有提交历史。
- 不提交当前工作区中与本轮无关的既有修改和未跟踪文档。
- 按“页面与分数”“英雄配置”“诊断接入”“文档与验收”拆分提交。
- 每个提交前检查暂存文件列表和 `git diff --cached --check`。

## 非目标

- 不修改 PC 后端；
- 不迁移狗粮和助手自动；
- 不重构英雄合成大文件；
- 不自动降低阈值；
- 不改变正式/实验功能状态；
- 不处理当前工作区的其他历史改动。
