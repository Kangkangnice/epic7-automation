## 这条路线在游戏里干什么

每天进骑士团把捐赠闭环跑一遍：资源支援页逐行看成员缺什么、自己持有够不够，够就点「支援」
把材料送出去；再请求一次当天支援、按进度领每周任务的里程碑奖励。**支援会把自己的材料送出去**，
点错行就是白送；请求支援每天只有一次，可领的里程碑档位还会随积分别处移动。判据拿不准时
一律退回「照旧点 / 照旧不领」的既有行为，宁可多跑一趟也不误判成「不足 / 已满 / 已灰」。

## 页面链路

```
骑士团活动·资源支援 → 逐行支援 → 支援确认 → 获得奖励弹窗 → 资源支援（下一行）…
  → 请求支援（选资源 → 确认）/ 每周任务（里程碑领奖）→ 收工
```

- 列表第一行是自己，按钮写「本人」而不是「支援 N 个」，不参与支援。
- 「请求支援」弹窗与「获得奖励」弹窗是两层不同的东西，谁来关决定业务后果（见判据节）。
- 可领档位的角标随积分在进度条上左右移动，不是固定在某一格。

## 判据为什么这么设计

每条写的是「靠哪一维排除外观同类、语义不同的对象」，不是调阈值的经验值。

- **「这一格能不能支援」先看数字、再看结果**：点之前读每行「持有：N」与按钮「支援 M 个」，
  N < M 就跳过、连点都不点（判据本体是模块级 `read_row_numbers`，不是类）；点之后没弹「获得奖励」就记进 `skipped_rows` 换下一格。
  ⇒ **排除「材料不足」那行一闪而过的浮字**：它瞬时出现、每秒取一帧必然漏检，「没看到」和「没出现」分不开 ⇒ 不做判据；用的「持有 / 需求」是**静态数字**，一直在画面上。
  认不出必须退回「照旧点」，不是误判成「不足」白丢积分。
- **PC「本人行」靠需求侧、不靠「持有读不出」**：第一行按钮写「本人」，需求侧读不出；拿「持有读不出」当代理跳掉这类行，会把「持有多位数」（字模只做 0~5，6~9 读不出）的别人行**一并跳过**。
  ⇒ 正确判据：`required is None`（按钮上没有「支援 N 个」）才是本人行；`holdings is None` 但 `required` 读得出 ⇒ 别人的行**照旧点**；
  整屏需求都读不出时不走这条，退回照旧点（字模整体失效，不能把能支援的人全跳掉）。
- **「请求支援」今天已用过 ⇒ 按钮变灰，靠相对亮度不靠模板**：变灰只是亮度变了、字形一样，`TM_CCOEFF_NORMED` 对亮度缩放不敏感 ⇒ **模板分认不出来**，「加张灰模板比谁分高」走不通。判据 `request_button_relative_v` 取**按钮区域相对整幅画面的亮度分位**。
  ⇒ **必须用相对亮度**：绝对阈值会被页面淡入骗（整屏压暗时塌掉，把「还有次数」误判成「次数用完」）；**底色不是判据**（褐底 / 深蓝底读数一致，只看亮度不看颜色），区域均值方向是反的、单像素最大值易被噪点顶起来。
  ⇒ 拿不准当作「还亮着」照旧点（fail-open）：误判「已灰」白丢当天唯一一次请求。
- **「今日支援上限」满没满，读整串数字而不是倒推**：满了列表绿按钮照样绿、点下去连提示都不弹 ⇒ 以前靠「连点推不动」倒推、日志写「多半是上限满了」，还会把「点击丢了」一律记成上限满。现在把右上角整串当一张模板，命中「满」就一个支援按钮都不点、直接切每周任务。
  ⇒ **整串命中排除「没满」的干扰**（同页干扰天然高、共享尾巴，阈值不能放太低）；**两条来路日志分得开**（画面证据写得分、兜底写「当时没读到上限数字」），**不许再出现「多半」**。
  认不出当「没满」（fail-open）：判成「已满」白丢当天整个支援环节。
- **里程碑可领档位随积分移动 ⇒ 搜整条带 + 补形态判据**：角标随积分跑到进度条别处，写死小方块只罩得住最低档 ⇒ 认不出 ⇒ 状态机走「没有可领的了」直接收工、奖励白丢，而理由读起来天经地义。修法改成**整条里程碑带**并补「角标长什么形状」（填充率）。
  ⇒ 带子放宽后「持有」绿字也落进来，它和角标一样高饱和 / 高亮、面积宽高都过筛，掩膜分不开 ⇒ 只有**实心圆点 vs 文字细线**的形态分得开。
  ⇒ 一屏多档先领最靠上那个「一次领一个」是先到先得不是漏检；放宽填充率前要确认图标碎块不会插到角标前面。别把单张样本的偶然（角标蓝或橙、绿✓被挡）当规律 —— 判据本就不看色相。
- **数字字模只有 0~5、别当万能**：任一侧含 6~9 读不出 ⇒ `None` ⇒ 照旧点；非基准画布整条判据弃权 ⇒ 照旧点。字模按高度归一化，跨「持有」绿字 /「需求」白字两套样式用。
  ⇒ **尺寸偏离基准超过容差时整条判据弃权**是刻意 fail-open，别为了「让它能跑」放宽；换客户端 / 分辨率各档重采。`None` 是「读不出」，不是「不足」，别并成一个结论。
- **PC「请求支援」弹窗：模板焊死了会变的持有数量**：弹窗正常打开，断点在页面组合判据 —— 花朵格子模板把**会变的持有数量**一起裁进去，数字一换分数就掉到阈下 ⇒ 整页判不出。修法是**裁掉数字行**（花朵图标、绿勾、金框都还在），判据与阈值一字未改。
  ⇒ **模板里不放会变化的内容**（活动标 / 数值 / 头像 / 段位字）。⇒ 分诊「缺少导航锚点 X」：先看模板里有没有放会变的东西、再看阈值 —— 「模板内容变了」的指纹是分数掉在中档，「场景换了」会掉到极低档。
- **支援成功后整节收工：全局守卫抢了弹窗**：支援成功弹的「获得奖励」层被**全局守卫**抢先关掉，`support-one` 的 `target_pages` 一帧都没成立 ⇒ 主循环按「原页面仍在、目标页未出现」用旧坐标重试 ⇒ 置 `support_closed` ⇒ 整节收工。两把尺认的是同一个弹窗、都满分命中，但**归属**（谁来关）决定后果。
  ⇒ 修法是**关掉这条路线上的守卫开关、不是改状态机**：模拟器本就没有这组 PC 专属守卫模板，关掉是恢复模拟器语义，与英雄合成传送奖励层被抢同一处理；其它路线保留守卫。
  ⇒ 排查口诀：看到「`dismiss-reward-notice` + 某动作重试 + 整节收工」，先查这个弹窗是不是路线自己的 `target_pages`，别去调阈值 / 补模板 / 怀疑点击。

## 危险边界

- **支援把材料送出去、不可撤回**；点错行的拦截：前置「持有 < 需求」跳过、本人行靠需求侧识别
  （不误杀别人行）、覆盖层 / 售罄判据齐全才点。请求支援每天唯一一次，认不出 fail-open 照旧点，
  绝不因拿不准白丢额度。判成「支援上限已满」会白丢整个支援环节，故认不出当「没满」。
- 全局守卫抢弹窗只能关本路线开关（不改业务规则、不全局撤），有反向护栏钉着。
- 认不出 / 超时 → 安全停止留证，不猜着继续点，见
  [TRANSITION_CONTRACTS.md](../TRANSITION_CONTRACTS.md)。
- 全局危险动作与拦截机制见 [SAFETY_MATRIX.md](../SAFETY_MATRIX.md) 第一节；
  **不许为了过单张截图降阈值**。
