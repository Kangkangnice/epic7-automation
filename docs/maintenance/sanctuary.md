# 圣域收菜（`sanctuary`）—— 维护手册

> 改这条路线之前先看这一份。判据的**实测依据**都写在代码注释里
> （`games/epic7/evidence/sanctuary.py` 的模块 docstring 是主力），
> 这份文档只负责「改哪里、缺口在哪、怎么验」。

## 这条路线要干什么（2026-09-29 新增；2026-09-30 追加「照料」）

每天一次，把圣域里刷出来的材料收掉：

```
大厅
  └ 左侧竖排菜单**最上面**那个「圣域」入口（在「光辉里程碑」上方）
圣域主页（右侧三行入口：精灵之森 / 欧勒毕斯之心 / 炼金术师之塔）
  └ 本轮只做最上面那一行「精灵之森」
精灵之森（三行材料：企鹅巢穴 / 精灵之泉 / 魔罗戈拉种植地）
  ├ 可领的行：蓝底白边在闪、中间「领取奖励」
  │     → 点一下 ⇒ 弹「…成长完成!」弹窗 ⇒ 点弹窗底部「点击关闭」
  │     → 回到本页，该行变成倒计时
  ├ 第三行右下方还有一颗「照料(1/3)」按钮（**加速第三行材料生长**）
  │     → 旁边那个计时器走到 00:00:00 它就变亮 ⇒ 亮着就点掉
  └ 三行都没有「领取奖励」、且照料按钮不亮 ⇒ 本轮收工 ⇒ 回大厅
```

用户原话：「每天这个圣域里面会定时刷新一些材料，然后我们需要定时去把它给点掉……
你去收菜就很简单把它点掉。」「目前的话只有部分刷新的，我们先把部分的这些流程给走通。」
（2026-09-30 追加拿「照料」：「第三行下面右下方有一个照料，照顾的意思，第三行的菜
可以通过这个方法点击之后，它可以加快它的生长，所以碰到这个量的话，跟其他一样，也点掉。
他点的话，应该没有弹窗。你可以看一下」）

## ⚠️ 与用户口述不符的那一条（实测为准）

用户说「点完之后它就是一个很小的弹窗，**也不需要你点**」。

**实测：弹窗不会自己消失。** 弹出 6 秒后再拍一帧（夹具
`tests/fixtures/epic7_sanctuary/popup_penguin_after6s.png`），弹窗仍在，
整幅平均亮度与刚弹出时一模一样，底部明写「点击关闭」+ 一个 ▼。

⇒ 路线必须自己点掉它（动作 `dismiss-claim`）。**别把这一步改成等待。**
`tests/test_sanctuary.py::test_the_popup_does_not_disappear_on_its_own` 钉着这一点。

## 判据：只有一个锚点，而且够用

| 锚点 | 区域 (x,y,w,h) | 阈值 | 正例最低 | 负例最高 | 全库最高 |
|---|---|---|---|---|---|
| `forest_row`（圣域主页判据 + 进精灵之森的点击点） | (1650,280,280,70) | 0.80 | 0.9999 | 0.2411 | 0.3569 |
| `forest_title`（精灵之森页标题） | (60,55,300,95) | 0.80 | 1.0000 | 0.3806 | 0.6496 |
| `claim_text`（**唯一的「可领」判据**） | (1470,418,430,400) | 0.80 | **0.9744** | 0.5498 | 0.4157 |
| `popup_close`（领取完成弹窗判据 + 点击点） | (840,800,300,70) | 0.80 | 1.0000 | 0.2310 | ⚠️ 0.9999（不排他，见下） |
| `care_text`（**照料按钮在不在**，不等于能不能点） | (1540,840,400,110) | 0.80 | 1.0000 | 0.3110 | 0.9517（全在圣域森林页，见下） |

用户列举的可领特征有五个（蓝底 / 白边框 / 闪烁 / 红点 / 「领取奖励」），**只用了最后一个**：

- **闪烁**不用管：12 帧连拍（间隔 0.4s）实测相邻帧差异 0.68~2.49、整幅亮度
  53.29~54.86 脉动 —— 它确实在闪，但**闪烁只把模板分数从 1.0000 压到 0.9744**
  （12 帧最低）。模板匹配是零均值归一化的，闪的是底色亮度不是形状。
  ⚠️ **不许为它降阈值** —— 0.9744 离 0.80 还有 0.17 的余量，改阈值只会削弱判据。
- **红点**不用：那是**通知角标**，玩家看过通知后它可能先消失而「领取奖励」还在
  ⇒ 拿它当**必需**条件会**漏领**。只做非必需的旁证，不进任何判据。
- **蓝底 / 白边框**不用：颜色在淡入与弹窗遮罩下都会变，是已知会骗人的一类判据。

### 三行材料的位置

药丸底 y 353..491 / 528..662 / 699..820，**行距 173**；「领取奖励」文字带：

| 行 | 材料 | 可领时文字带 (x, y) | 不可领时写什么 |
|---|---|---|---|
| 1 | 企鹅巢穴 | 1505..1610, 430..461 | 倒计时（实测 `10:11:23`） |
| 2 | 精灵之泉 | 1505..1610, 603..634 | 倒计时（实测 `20:23:39`） |
| 3 | 魔罗戈拉种植地 | 1505..1610, 776..807 | 倒计时（实测 `96:08:55`） |

⇒ 整条带子一次 `find_all_templates` 就把「现在有几行可领」全找出来，行距 173
远大于非极大值抑制半径 60。

### 「照料」按钮：能不能点，**不许**用按钮亮度判

位置：亮绿药丸 `x1604 y871 w247 h43`，在第三行药丸**下方偏右**；同一行左边有个
**冷却计时器**（实测 `00:00:00` 时按钮亮、`00:22:10` 时按钮灰）。

⚠️ **绝对亮度是被实测否掉的方案**（不是没试过）：亮 113.8 / 灰 56.6 看着能分，
但圣域是 **3D 昼夜场景**、药丸**半透明** ⇒ 拿一个**状态完全相同**的参照物
（第 3 行药丸，两帧都在倒计时）量一下，它自己就随背景差了 **42 点**。
也就是说那 57 点里大部分是**背景变了**；白天冷却中的按钮会被误判成可点，
而那是**会真点下去**的。

✅ 实际用的是「**文字白不白**」：亮态「照料」是纯白（峰值 255，框内 15.92% 的像素
亮过 235），冷却中是灰的（峰值 147，0.00%）。它与背景无关（说的是文字自己的颜色）。
代码在 `evidence/sanctuary.py::probe_care`，常量为
`CARE_TEXT_WHITE_LEVEL = 235` / `CARE_TEXT_WHITE_MIN_RATIO = 0.02`。

**为什么模板分不出亮/灰**：`TM_CCOEFF_NORMED` 是**对比度归一化**的，对「形状一样、
明度不同」天然失明（实测两态都 0.95~1.00）。⇒ 「按钮在不在」与「能不能点」必须是
**两道独立判据**，缺一不可。回归用例
`test_the_dim_care_button_is_not_clicked_even_though_the_template_still_hits` 与
`test_absolute_brightness_would_have_been_the_wrong_judgement` 都钉着这一点。

## ⚠️ 三条决定写法的实测事实

1. **行必须按 y 排序，不许按分数排序。** 实测第 1/2 行的分数只差 0.001~0.01，
   而且帧间互相反超（`forest_two_claimable_08` 上第 1 行 0.9733 **低于**第 2 行 0.9744）。
   按分数排的实现在两行之间来回跳，表现是「同一个材料被反复点、另一行永远轮不到」。
   代码在 `evidence/sanctuary.py::claimable_rows`，回归用例
   `test_rows_are_ordered_top_to_bottom_not_by_score`。

2. **弹窗必须判在精灵之森『之前』。** 弹窗只把底页压暗，底页标题 `forest_title`
   在弹窗下**仍然 0.9998**（≥0.80）⇒ 只靠它分不出「弹窗开着」和「弹窗关着」。
   顺序反了的后果：对着一页盖着弹窗的画面去点「领取奖励」，那一下点在遮罩上、
   什么都不发生，然后重试到报错。判定顺序在 `games/epic7/sanctuary.py::_PAGE_STATES`。
   ⚠️ 顺带一个有用的副作用：弹窗开着时 `claim_text` 只有 0.5498 ⇒ 即使顺序写错也不会
   误点「领取奖励」。

3. **导航层必须认得圣域主页**（`navigation.observe()` 的 `sanctuary_home`）。
   少了它，「大厅 → 进圣域」那条转场永远验收不通过 —— `_transition` 靠
   「`observe()` 报出目标页名」才算成功，症状是转场等到 92 秒超时、重试 4 次后报错。
   锚点**复用** `evidence/sanctuary.py` 的 `forest_row`（不另存一份），
   与 `lobby_worldboss_select_team` 复用 `world_boss` 的图同一个道理。

### 为什么「两帧稳定确认」足以挡住淡入那一瞬间

弹窗**淡入**（以及关闭时的淡出）会经过一段「遮罩半透明」的区间：`claim_text`
掉到 0.80 以下、`popup_close` 还没到 0.80 —— 这个区间里页面会被判成「精灵之森且
没有可领行」，看起来像「今天收完了」。

它不会造成误判，因为：**这个区间只持续几十毫秒，而主循环的取样间隔是 1 秒。**
连续两帧（间隔 1s）不可能同时落进一个几十毫秒的窗口 ⇒ 主循环的「连续两帧一致才
采信结论」（`StableObservation` + `ConclusionGate`）天然挡住了它。
⚠️ 别把 `poll_seconds` 调到 0.1 以下，那样这条论证就不成立了。

## 转场契约（`_REQUIRE_TRANSITION_CONTRACT = True`，本项目第四条）

| 动作 | 来源 | 出口验收 | 理由 |
|---|---|---|---|
| `open-forest` | 圣域主页 | `target_pages` = 精灵之森 | 换页 |
| `claim-row` | 精灵之森 | `target_pages` = 领取完成弹窗 | ⚠️ **刻意用 `target_pages`**：弹窗确实会弹（两次实点都弹了且不会自动消失）⇒ 「弹窗出现」是可靠的出口证据。万一某次点击没生效，弹窗不出现 ⇒ 8 秒后**用同一个坐标**重点（最多 4 次），然后**响亮地失败**（留诊断 + 退出码 1），而不是悄悄跳到下一行 |
| `dismiss-claim` | 领取完成弹窗 | `target_pages` = 精灵之森 | 换页 |
| `care` | 精灵之森 | `in_page_evidence` = 按钮由亮（白字）转灰 | ⚠️ **不换页** ⇒ 主循环不为它对账转场；把关靠「下一帧重新判页面」。若它其实会弹窗（没验证过），下一帧会认出弹窗并转去 `dismiss-claim`，也不会卡住 |

⚠️ **`_on_action_exhausted` 刻意不覆写**：基类默认（返回 `False`）会「给一次换个办法的
机会 → 留诊断 + `RuntimeError`」⇒ 退出码 1 + 失败通知。曾经写成「自己留诊断 +
`return True`」，那是错的：`True` 的语义是**已优雅收尾**，主循环正常返回 ⇒ 退出码 **0**、
通知写「已完成」—— 用户看到「任务完成」而实际一个材料都没领到。

## 已知缺口（写在这里，别装作不存在）

| 缺口 | 影响 | 补法 |
|---|---|---|
| **只做了「精灵之森」这一行**。圣域主页另外两行（欧勒毕斯之心 / 炼金术师之塔）本轮完全不碰，它们的页面长什么样一次都没采过 | 那两行里的材料永远收不到 —— 用户原话是「目前的话只有部分刷新的，我们先把部分的这些流程给走通」，所以这是**已知且被认可**的范围 | 要么各开一条路线，要么把本路线扩成「三行依次进」。先得各采一个页面的帧 |
| **`lobby_sanctuary` 只有一张候选图**（大厅左侧「圣域」文字标签） | 对比「秘密商店」入口那两条候选（干净版 + 带角标版）：若游戏改了左侧菜单的字体或行高，这个入口当场认不出，整条路线进不去 | ⚠️ 我们**没有**一张「圣域入口挂红点」的大厅帧。模板截的是**文字标签**、红点在**图标**上，理论上互不干扰 —— 但**没验证过**。下次红点出现时截一张，就能像秘密商店那样存第二条候选 |
| **`popup_close` 不排他**（全库最高 0.9999） | 它是游戏**通用**的「获得奖励」弹窗底部控件（英雄页 / 骑士团捐赠都命中）。命中是**对的**（确实是同一种控件），而且动作只是「点掉它」、**无副作用**，所以不构成风险 —— 与 `knights_donation.reward_title` 同源 | 不需要修。真要修就得给「领取完成」弹窗找一个专属锚点，而那个弹窗**标题与物品图标每次都变**（「企鹅成长完成!」vs「下级精灵之花成长完成!」），没有稳定特征 |
| **第三行（魔罗戈拉种植地）从没被观测到可领** | 三行共用一张 `claim_text`、靠区域分别命中，所以第三行理论上不需要额外判据 —— 但**没有正例** | 下次它可领时截一帧，就能验证「第 3 行文字带 776..807」这个实测值 |
| **「点照料没有弹窗」是用户的判断，我没实点过**（用户 2026-09-30 明确「先别点，我自己来」） | 若实际会弹窗：动作本身仍能走完（下一帧会认出弹窗并转去 `dismiss-claim`），**不会卡住**；但它声明的 `in_page_evidence`（「按钮转灰」）就不成立了，日志会误导 | 用户自己点一次就能证伪。若真弹窗，把 `care` 的出口验收改成 `target_pages` = 领取完成弹窗 |
| **亮态「照料」只有 1 帧样本**（`forest_care_ready.png`） | 15.92% 是**单点**，没有方差；冷却态有 10+ 帧（全 0.00%）。另外这一帧是**白天**背景，而所有冷却态帧都是夜景 ⇒ **「白天 + 冷却中」这一格没有样本** | 补法：让用户在同一时段（背景不变）点一次照料，抓「点前 / 点后」两帧 ⇒ 背景被约掉，阈值与「点一次会不会转灰」一次全钉死 |
| **`care_text` 的「全库最高 0.9517」全是圣域森林页** | 全库 293 张夹具扫下来，越阈的**只有** 8 张 `epic7_sanctuary/forest_*`（都是真命中），**零误报** | 不需要修。但新增森林页夹具时留意：若哪天有非森林页越阈，就要像 `forest_row` 那样缩区域 |
| **不读金额 / 数量** | 领到几个材料不解析，只在日志里写「点掉了哪一行」 | 与骑士团捐赠的取舍一致（用户 2026-09-25 当场拍板「先不读金额」）。真要做就走独立数字模板通道，别塞进判页锚点 |
| **`sanctuary_title.png` 不存在**（刻意） | 圣域主页的判据用的是右侧第一行「精灵之森」，不是左上角标题 | 第一版用的就是 2 字标题「圣域」，被全库扫描否掉：`epic7_fodder/stage_3_7.png` 的标题叫「**圣域**最深处」，前两个字恰好就是「圣域」⇒ 那张模板在那里得 **0.9784**（越阈）。**教训：短标题模板可能是别的标题的前缀。** `tests/test_project_layout.py::test_sanctuary_templates_exist` 钉着「它不许回来」 |

## 怎么验

```bash

D:\anaconda\python.exe auto_game_unified\tools\check.py --files games/epic7/sanctuary.py

# 改了 modes.py / navigation.py / daily_tasks.py / desktop/** 这些共享模块 ⇒ 全量
```
