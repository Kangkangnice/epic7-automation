# 路线终点（Route Finish Points）

> 用户 2026-09-25 定下的规矩：**每条路线都必须有一个明确的「终点」，`
> `return home` 一律只在终点衔接。**
>
> 本文件的用途有两个：
> 1. 把「终点」这件事**定义清楚**（下面第一节）；
> 2. 把 10 条路线**各自的终点逐个标出来**给人审（第三节那张表）。
>
> 为什么要单独立一页：`return home` 之前踩过的坑，根因都不是「回家逻辑写错了」，
> 而是**「终点划错了」** —— 拿一张路线还没走完的中间帧当终点喂给回家流程，
> 于是回家流程去处理它根本不该管的页面（详见第二节的实例）。

---

## 一、什么叫「路线终点」

**终点 = 这条路线把该干的活干完之后，主动停手的那一页（或那一段链路）。**

它同时是两件事的分界线：

```
…… 路线自己的业务逻辑 ……  │  ← 终点 →  │  …… return home 接手 ……
```

终点**必须**满足一条硬要求：

> **站在终点上时，人已经出局了。**
> 不在战斗里、不在房间里、不在任何**带浮层的页面**里（商人商店、购买确认框、
> 奖励弹窗……）。

### 为什么必须有这条硬要求

因为 `return home` 送人回去，靠的是**右上角那颗蓝色四格**（打开快捷菜单 → 点酒馆 → 到家）。
而那颗四格**在带浮层的页面里是灰的、点不动**，但模板匹配**照样认得出它**
（`TM_CCOEFF_NORMED` 对整体明暗缩放不敏感）—— 于是回家流程会去点一颗死按钮。

实测数据（`tests/fixtures/epic7_labyrinth_stone/shop.png`，迷宫商人商店）：

| 帧 | 蓝四格匹配分 | 实际状态 |
| --- | --- | --- |
| 大厅 | 0.8928 | 可用 ✅ |
| 迷宫详情页 | 1.0000 | 可用 ✅ |
| **商人商店（局内，浮层压暗）** | **0.9053** | **灰的，点不动** ❌ |

**0.9053 高于阈值 0.82 ⇒ 光看模板分分不出「亮四格」和「灰四格」。**

所以「终点必须已出局」不是洁癖，是**让回家流程永远碰不到灰四格**的唯一办法。
（另一条路是给回家流程加「先判在不在局内」的补丁，但实测那个判据在商店帧上也失效：
局内标志 `‖` 被浮层一起压暗，从 1.0000 掉到 **0.5588**，低于阈值 ⇒ 两道防线同时失效。
**结论：靠判据防不住，只能靠「把终点划对」。**）

### 端点可以是「一条链路」，不一定是「一页」

迷宫的终点就不是一页，而是一段：

```
商店里确认买不到强化石了
  → 点左上角返回箭头，离开商店（路线自己做的，动作名 leave-shop）
  → 回到商人房
  → 开暂停菜单 → 放弃战斗 → 确认「结束」（路线自己做的）
  → 落到迷宫详情页   ← ★ 这里才是 return home 的起点（人已出局，四格是亮的）
  → 蓝四格 → 酒馆 → 大厅（return home 做的）
```

**「局内的收尾」属于路线自己，「从非局内页回大厅」才属于 return home。**

## 二、踩过的坑（为什么要把终点定义清楚）

2026-09-25 开发 `return home` v2 时，我（AI）拿 `shop.png` 当终点去驱动新流程，
结果它去点了灰四格。当时一度以为是「回家流程缺一条判据」，
追到后来才发现**是终点划错了**：

- 迷宫路线本来就会自己 `leave-shop` 退出商店（`labyrinth_stone.py:_at_shop`）；
- 商店那一帧**根本不会**出现在「路线已收工」的时刻；
- 是我的假测试序列造了一个现实中不存在的状态。

**教训**：回家流程的判据再准，也救不了「拿错帧当终点」。
所以新增/修改路线时，**第一件事是回答「我的终点在哪」**，而不是先去调回家流程。

### 注 ①：arena 的终点**曾经不合格，已修**（2026-09-25）

**问题**：翻 `runtime_logs/epic7_arena.log`，票耗尽的收工现场在
`runtime_diagnostics/epic7_arena/20260925_081722_997139_ticket_exhausted.png` ——
**画面是「购买旗帜」弹窗**：

```
购买旗帜
  友情点数   一天可购买1次   18小时后可购买     [30] → [5] 持有=13191
  [取消]            [购买]
```

⇒ 票耗尽时人停在**浮层**里，不满足「已出局」。回家流程从这儿起手会撞上
左上那颗灰的「战斗开始」和弹窗按钮。这也是历史上日志里 8 次卡在这里反复刷的成因之一。

**修法**（已落地）：把 arena 的终点**下移一步** ——
`_close_out()` 里先调 `_dismiss_purchase_popup()`：

1. 判据用**双锚点** `purchase_title`（「购买旗帜」标题）+ `purchase_cancel`（「取消」）；
2. 命中就点「取消」，然后**等画面真的离开弹窗**（最多 5 秒）；
3. **认不出就一个点击都不发**（fail-closed）；点了关不掉也不硬来，
   记一笔「购买弹窗未关闭」照旧收尾（不改退出码）。

⚠️ **为什么非要两个锚点**：单靠「取消」两个字会**串门** ——
全屏搜的时候，迷宫「购买确认」「放弃确认」分别得 **0.9757 / 0.9758**，会被误点掉。
加上标题后那两张掉到 0.8044 / 0.4981（都不过 0.90）。
另外两条判据都加了**区域限定**（按竞技场弹窗位置定的框），迷宫弹窗根本不落在里面。

改动落在 `arena.py`（`_dismiss_purchase_popup` + `ArenaTemplates` 两个新字段）与
`evidence/arena.py`（区域 / 阈值 / 模板路径三处）；
测试 `tests/test_arena_purchase_popup.py`（判据串门 + **真 Runner 级**收尾接线）。

⚠️ 同理，`arena.py:1385`「今日友情点旗帜已购买」那个出口把状态硬改成
`ArenaState.BATTLE` 再 `_close_out()` —— **状态和画面不一致**。
它现在被 `_close_out` 里的兜底一起覆盖了（那条路若弹窗已弹出也会被关掉），
但那个多余的赋值本身值得清（**本次没动**，避免混进无关改动）。

### 注 ②：fodder 的异常出口（优先级低）

「生命之叶确认多次未生效」时**弹窗还开着**，同样不满足「已出局」。
但这是**异常路径**（点不动才走到），先记着，不阻塞本次。

## 四、新增路线时怎么做（准入清单）

按 `topics/route_admission.md` 那套「登记四处」的格式，**再加一问**：

1. ~~在 `MODE_SPECS` 注册~~（既有）
2. ~~声明接力立场~~（`RESUME_EXEMPT`，既有）
3. ~~声明转场契约立场~~（`TRANSITION_EXEMPT`，既有）
4. ~~声明收尾回首页立场~~（`FINISH_HOME_EXEMPT`，既有）
5. **★ 新增：回答「我的终点在哪」** ——
   - 正常跑完停在哪一页？
   - 资源耗尽停在哪一页？
   - **这两处，人出局了没有？**（没有 ⇒ 要么路线自己先退出局内，要么写进豁免表说明）

第 5 问的检查方式：终点那一帧**必须**能在蓝四格上拿到高分 ——
也就是「人已出局」的等价表述。可以拿一张终点帧直接量刑：

```python
# 终点帧上蓝四格的匹配分必须过阈值（口径见第一节的表）
find_template(screen, quick_menu_button, 0.82, region=..., reference_size=(1982, 1132))
```

## 五、`return home` v2 与终点的分工

| 谁做 | 做什么 |
| --- | --- |
| **路线自己** | 把「局内」的事收干净：退出商店、放弃战斗、关掉浮层 ⇒ **走到终点（非局内页）** |
| **return home v2** | 从终点出发：**蓝四格 → 酒馆 → 大厅**；认不出就按 **ESC** 兜底 |

v2 的出口接线（`main.run_mode`）：

| 出口 | 退出码 | 回不回家 |
| --- | --- | --- |
| 正常跑完 | 0 | ✅ |
| 资源耗尽 | 2 | ✅ |
| **异常结束** | 1 | ✅（**v2 新增**；老流程刻意不接，用户 2026-09-25 拍板「一旦报错，代码已经结束了」） |
| 手动停 | 130 | ❌（用户喊停，再动游戏是添乱） |

⚠️ 异常出口要回家，意味着**异常发生时人可能还在局内**（路线没走到终点就挂了）。
这是 v2 唯一需要「兜住局内」的场景 —— 补丁的边界就在这儿，**第 10 条迷宫的
`_give_up_because` 走的也是这条路**（记真实原因 → 回家 → 报错）。

### 怎么接的线：`main.HomeReturn`

「回大厅」这一步由 `main.HomeReturn` **一个对象**统一入口。2026-09-26 起它已经**只是一个转发壳**
（`return_home()` → `navigator.return_home`，而后者自己就是 v2 的薄封装）：原先「这条路线走新流程
还是老流程」的白名单分派整段删除。现在 4 个调用点
（`_enter_mode` / `_install_finish_home` / `daily_tasks.ensure_at_lobby` / 异常出口）全走它
（第 5 个 `recover_to_mode` 随「回大厅恢复」那条通道一起删除，见 `docs/ARCHITECTURE.md`）。

**为什么不直接把 `navigator.return_home` 换成 v2**（问过用户，用户 2026-09-25 拍板
「不要省事，要规范」）：覆盖实例方法会让这一步**没法被替换**，测试想用假实现顶掉它
来单测别的逻辑就顶不掉；立一个明确的对象之后，这件事就直白了。

⚠️ 保留这个入口还有一个实际好处：调用形状（有没有 `stop_probe`）只在这一个地方说了算 ——
开局那一次「回大厅」要挂接力探针、收尾那一次不挂，差别写在一处（有测试守着）。

### 白名单进度（2026-09-25 晚）

| 路线 | 状态 |
| --- | --- |
| `arena` | 已实跑验收（2026-09-25，退出码 0、2 轮） |
| `world_boss` | **已加入，待实跑验收** |
| `knights_donation` | **已加入，待实跑验收** |
| 其余 7 条 | 仍走老流程（`navigation.return_home`） |

后两条是一起加的，起因是当晚每日任务实跑：骑士团捐赠卡住后交回**老**流程，
老流程在「资源支援」弹窗页上认不出画面 ⇒ 触发它内置的「点画面中央」唤醒 4 次
（落在列表空白上，全废），最后还是靠按 ESC 出去的。**v2 没有那一步** ——
认不出的页面直接走 ESC 兜底。验收重点：① 两条主页上「蓝四格 → 快捷菜单 → 酒馆」
能否一步到家；② 卡在弹窗页时 ESC 兜底能否干净退出、不许同一层连按两次。

### v2 的节奏：按完 ESC 要**等 4 秒**再判下一帧

v2 在「认不出这一页」时会按 ESC 退一层，按完**必须等画面真的翻过去**。
这个等待是实跑逼出来的（2026-09-25 竞技场验收，日志原文）：

```
19:25:04 模式=导航 流程=v2 动作=按ESC 原因=兜底 次数=1/8
19:25:06 模式=导航 流程=v2 动作=按ESC 原因=兜底 次数=2/8
```

中间只隔 2 秒 ⇒ **同一层退了两层**，白烧两次返回预算（上限只有 8 次）。

对比：老流程靠 `navigation._BACK_RETRY_SECONDS = 15` 规避，**15 秒太慢**
（用户原话「层数多一点就不太行」），v2 原先只等 1 秒**太快**。
用户 2026-09-25 拍板取折中 **3~5 秒**，实现取中值 4 秒：
`home_return.py::_ESC_SETTLE_SECONDS`。

⚠️ 不要图快把它调回 1 秒 —— 有测试钉着这个区间
（`test_home_return_failure.py::test_esc_waits_long_enough_for_the_screen_to_turn_over`，
断言的是 3~5 秒**区间**，区间内微调不打红，调回 1 秒必红）。
