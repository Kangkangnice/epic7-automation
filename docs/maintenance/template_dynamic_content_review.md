## 四、评审时用的四条判据

1. **「会不会变」×「是不是数字」** —— 判据是前者。固定的按键提示 `1/2/3` 属于骨架，保留。
2. **「数字占模板多大」** —— `support_limit_full`（110×27，**整张就是数字**）数值一变**直接失配**；
   `bonus_reward`（1100×750）里数字只占 0.64% ⇒ 只是小幅掉分、**仍过阈**。
   ⇒ 不能只看「有没有数字」，要看「**占多大 + 会不会变**」。
3. **「想读数值 ≠ 往锚点塞数值」** —— 真需要读数值走 `knights_donation/digits/` 那条独立通道。
4. **裁剪会不会带动点击点** —— **多数锚点的点击点 = 模板命中框中心**（`match.center`）。
   - **从顶部裁 N 行 ⇒ 中心下移 N/2**（左右同理）。
   - **要保点击点不变，就左右/上下对称裁**（本次 A3/A4 就是对称裁 125）。
   - 若无法对称裁（如 A2 的底部行），就得评估「点击点漂移后是否还在可点区」，或放弃改。

### 5.1 更正：`support_one_button` / `support_confirm_button` **不是**固定文案

我在 C 类里把「支援1个」判成「固定文案，保留」—— **错了**。用户当场质疑：
「有一些材料，它是真正多个的，你这个一个也不固定吧」。**查证成立。**

- `docs/maintenance/knights_donation.md` 第 21~24 行本来就写着
  「读每行的『持有：N』与**按钮上的『支援 M 个』**」，且实测表里 **M 出现过 1 / 2 / 4**。
- **实测**（线上口径 region `(1520,350,310,700)`、threshold 0.80、min_gap 60）：

  | 帧 | 按钮实际文字 | 模板「支援1个」得分 |
  | --- | --- | --- |
  | `support_page.png` | 支援1个 | 1.0000 |
  | `support_page_two_buttons.png` | 支援1个 ×2 | 0.9360 / 0.9278 |
  | **`support_page_short_material.png`** | **支援2个 / 支援4个** | **0.8542 / 0.8517** |

- **当前还过得去、但已贴边**：0.85 > 0.80，**余量只剩 +0.05**（全是「1」时是 +0.136）
  —— 与 `points_label` 同一性质。好消息是**命中位置完全一致**（(1681,569) / (1681,764)），
  因为按钮绿底占模板大部分、白字只占一小块 ⇒ **点击点不受影响**。
- **后果**：万一数字变化更大（如两位数）或游戏微调按钮，掉破 0.80 ⇒
  `_support_candidates` 找不到那一行的按钮 ⇒ **那一行被漏掉、少支援一次**
  （**不会点错，是漏做** —— 这一步是"少拿积分"，不是"点错地方"）。
- **建议（待用户拍板）**：**加变体模板** —— 把「支援2个」「支援4个」的按钮也各做一张，
  `_support_candidates` 改成逐个模板试、合并结果（思路同 `start_mission` 的双模板取高分）。
  覆盖实测全部已知情况，余量可回到 0.93+。
  ⚠️ **不要靠降阈值解决**（等于偷偷放松判据）。

### 5.2 `hero/sss_material_warning_title.png` 的「66」是 OCR 误报（已核实）

- **用途**：**英雄合成**路线。用「献身技能达到 SSS 级别的英雄」当材料时，游戏弹一个警告弹窗
  （「并不会达成…成就」），程序认到就点「点击关闭」关掉、继续跑
  （`hero_synthesis.py::_sss_material_warning_close` → 动作 `close_sss_material_warning`）。
- **OCR 认错的后果 = 零**：OCR 只在**本次普查**里离线跑过一遍，**不在程序运行路径上**
  —— 程序跑的是**模板匹配**。把 `SSS` 读成 `66` 只让普查清单多一条待人工确认项。
- **为什么认错**：那是**描边/空心艺术字**，`S` 的轮廓与 `6` / `8` 相近，属 OCR 模型固有局限。
