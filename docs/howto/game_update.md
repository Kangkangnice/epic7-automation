# 游戏更新与多人维护

用[兼容跟踪表单](https://github.com/Kangkangnice/epic7-arky-assistant/issues/new?template=game_update.yml)为一次游戏更新建一条 Issue。
维护者记录游戏区服、公告或可见版本、客户端系列及版本、
助手版本或提交，以及已验证和待验证的路线。Windows、DPI、分辨率、语言和匿名账号阶段按问题补记。
同一更新的报告链接到跟踪 Issue，子问题只保留可独立复现和修复的范围。

## 1. 先判断用户影响

| 现象 | 维护动作 |
| --- | --- |
| 可能误点、重复提交、异常扣费或隐私泄露 | 请用户长按 P 键或点「安全停止」，先核对业务结果。停止受影响组合的试用和放行，经[安全政策](../../SECURITY.md)的私密渠道取证。 |
| 多条路线同时入场失败、黑屏或识别停住 | 优先查窗口捕获、权限、画布、全局弹窗和回大厅等共享能力。评审者确认受影响的客户端和仍可用的组合。 |
| 单一路线、账号阶段或选项失败 | 在路线证据层复现差异，保留当前帧、最后动作及预期终点，补最相似反例。 |
| 新英雄、新卡池或常规换期 | 先看改动内容。只有英雄数据时走图鉴入库，活动页面变化则另验对应路线。 |
| 升级后多台机器安装或启动失败 | 核对发布附件的校验值，从干净环境复现，按[发布手册](release.md)评估回退。 |

用户按[故障排查](../TROUBLESHOOTING.md#提交有效问题现场)提供最小脱敏证据。公开 Issue 只记录
复现步骤、匿名使用条件和已遮盖的必要片段。完整诊断包、账号标识、余额原图、路径和密钥保留在本机。
维护者按「待复现 → 已定位 → 待验收 → 已发布」更新同一 Issue，并指向当前负责人与下一步。

## 2. 按变更范围复验

先核对正式公告与客户端实况。公告未写清的行为，以真实页面和原有回归为依据。

| 改动 | 起点与重点 |
| --- | --- |
| 新英雄头像、名称、属性 | 按[英雄图鉴流程](../maintenance/hero_roster.md#二新增一名英雄日常一条命令)入库。验竞技场头像匹配、优先/避战名单和桌面筛选。若同时上线新支线或召唤界面，分别处理对应页面。 |
| 活动、赛季、个别路线页面 | 对照该路线维护手册，回放旧版、当前版、账号变体和相似页面。变更危险按钮时核对授权、价格、业务回执和终点。 |
| 大厅、公共弹窗、字体、截图、输入 | 从正常入口和共享层定位。核对所有依赖方的离线测试，挑受影响的高风险路线在声明的各客户端实机复验。 |

从仓库父目录运行以下命令，查看已提交改动与主分支之差关联的回归：

```powershell
python -m auto_game_unified.tools.check --plan --since origin/main
```

也可用 `--plan --files <仓库相对路径>` 预查改动，已暂存时可直接用 `--plan`。
它根据模板、夹具和代码的使用关系给出回归范围，
维护者仍需按公告和实机确认客户端变动。用失效判据自己的正反例校正搜索区域和阈值，遵守
[转场契约](../TRANSITION_CONTRACTS.md)的公共安全门槛。未知或冲突页面安全停止。

## 3. 小范围验证、发布和回退

1. 开独立分支，关联跟踪 Issue。负责人注明风险、回归证据和受影响组合。路线内用独立修复，
   共享层改动在 PR 中列出传播范围。
2. 从正常入口干跑并完成授权范围内的一轮。先在已说明风险的试用组合小范围验证，
   按[路线稳定版验收](route_acceptance.md)逐客户端登记真实终点和账号差异。一次跑通记开发通过。
3. 稳定版按[发布手册](release.md)构建和复核。同一份发布说明写清助手版本、适用的游戏版本、
   已通过的组合、延期组合与恢复条件。维护者复核 Issue 和发布附件，使用新版本号发布修订。
4. 发现回归时先撤回受影响组合的支持声明，通知用户停用相应路线。只在同一游戏版本仍兼容且有
   证据时建议使用旧助手版本。客户端本身已变时保持受影响组合暂停，按证据修复。
   已确认的交易或领取先对账，避免重跑。

未完成的实机验证按[交接约定](../README.md)进入在制记录，保持一个责任人、当前证据和可执行下一步。
完成后把可复用结论写回路线维护页或回归测试，公开变化进变更记录，撤下临时跟踪记录。
小范围先验收再扩大范围的流程参考 [Google SRE 的试发布实践](https://sre.google/workbook/canarying-releases/)。
