# 一句话说清这份手册教什么

> **这份文件是「手法」类文档**：具体怎么操作、失败了怎么判。
> 与其它三类的区别 —— 现状（系统现在是什么样）在 `STATUS.md`；决策（当初为什么这么定）
> 在 `docs/decisions/`；过程（这次改了什么）在提交信息与 `CHANGELOG.md`。
>
> 复制本文件到 `docs/howto/<英文短名>.md`，然后在 `docs/README.md` 的
> 「按你要做的事找」表里加一行（不加会被门禁拦下）。
>
> ⚠️ **旧做法不要新建一份文件**，改这份。一个 `topic` 只允许一份 —— 门禁会查。

## 一、先跑自检（如果有的话）

能写成命令的就别写成说明。一条命令跑完能给结论的，比读三段文字可靠得多：

```powershell
python -m auto_game_unified.tools.<你的自检工具>
```

## 二、标准做法

按「场景 → 命令 / 步骤」写。**每一步都要能被执行**，不要写"配置好环境"这种没法验证的话。

| 我要做什么 | 怎么做 |
|---|---|
| | |

## 三、失败了怎么判

这一节最省时间：把「现象 → 病因 → 下一步」列清楚，别让人猜。

| 现象 | 病因 | 下一步 |
|---|---|---|
| | | |

## 四、每条做法的依据与作废条件

**没有依据的做法会被下一个人当迷信删掉**，那也是一种损失。同理，不写"什么时候作废"，
这条做法会在条件变了之后继续被遵守。

| 做法 | 依据（当时实测到什么） | 怎么复核它还有效 | 什么情况下作废 |
|---|---|---|---|
| | | | |

## 五、作废的做法（墓碑）

旧做法**不要直接删掉**，留一行在这里。原因：下一个人（或 agent）可能记得旧做法，
会去搜那些旧词 —— 搜到墓碑就知道"这条路走不通了"，而不是搜不到就自己再试一遍。

- 已作废（2026-01-01）：原做法 X，因为 Y，现在看上面第 N 节。
