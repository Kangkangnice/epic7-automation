# 路线开发与验收

先确定这次要支持哪些玩家和设置，再说明什么算做完、怎么验证、何时可以公开支持。新增路线、游戏更新、故障修复和共享行为变更都按这份规则走。

## 1. 先定义这次交付

按**路线、后端、客户端及版本、待验提交、设置分支**逐个验收。雷电、其他模拟器、STOVE 和 Steam 分开记，写清已验的 Windows、语言、窗口尺寸和输入方式。默认设置、资源开关、只读和实际业务分开列，注明会改变结果的账号状态、玩家入口和可接力的起点。

开工前写清每个受影响分支的验收合同。已有合同可以引用，把本次变动和要复验的地方点出来。

| 要写清的事 | 要回答的问题 |
|---|---|
| 入口与设置 | 从大厅、每日编排、路线中途还是约定的手动起点开始？哪些选项打开？ |
| 业务目标与数量 | 要做成什么、按什么单位计？写明请求量或可观察的自然终点。 |
| 资源与授权 | 单次启动可以用哪些资源、各有多少？哪些付费项默认关闭，哪些对象禁止触碰？ |
| 业务回执 | 哪一页、哪一行或哪个读数证明结果已发生？看不到回执时怎么办？ |
| 合法终点 | 在哪里收尾，如何确认已脱离局内及浮层？默认回大厅；有收尾豁免时写明终点和串跑限制。 |
| 提前停止 | 哪些空态、冷却、额度耗尽等条件允许停止？各自要看到什么，怎样安全收尾？ |

路线还要明确终点、覆盖层、空态、动作回执和危险动作，单条路线的画面和资源边界见各自维护手册。[路线通用契约](../ROUTE_CONTRACT.md)

| 变更 | 最小验收范围 |
|---|---|
| 新增路线或扩大支持 | 新增组合从正常入口到完整业务和终点，覆盖相关反例。 |
| 游戏更新、维护或移植 | 复验变化分支及相邻既有分支。移植时实机验证目标 PC 客户端，保留原有模拟器回归。 |
| 修故障 | 先留第一处故障证据，用现场复现旧问题，再验证修复、相邻反例及受影响的正常入口、业务结果和收尾。 |
| 改共享行为 | 列出实际经过该逻辑的路线、入口和输入方式，覆盖这些调用者。共享或未登记的运行改动做全量离线回归，优先实机复验受影响的高风险组合和本次扩大范围。 |

一项改动符合多行时，合并各行范围。游戏更新造成的兼容变化按更新手册处理。[游戏更新手册](game_update.md)

## 2. 每个动作要有证据

点击、滑动、返回、处理弹窗、移交战斗和收尾等动作，凡是会改变页面、选择、资源或业务状态，都要沿实际执行过程确认五段证据。

1. **来源进入**。确认当前页面、所处状态、目标对象和控件可用。写清会挡住动作的遮罩、禁用态、相似对象和未知状态。
2. **候选动作**。说明允许发出什么输入、预期去哪里、副作用及预算，发出时只记录一次尝试。
3. **来源退出**。确认旧页面或页内状态确实退出，能识别加载、动画、黑屏和冻结。
4. **目标进入**。用正向判据确认目标页面或页内新状态稳定。结束时也要验证约定的终点。
5. **业务完成**。看到真实回执再计数，每笔只记一次，同时核对实际用量。纯导航动作到达可用目标即完成本步。

留在同一页时，要能区分前后状态，例如从可购买变为同一商品已购。页面和结论按稳定门槛确认，使用新采的相邻画面。来源退出、目标进入和业务回执分别取证，冻结画面和缓存重复帧不计。[页面转场契约](../TRANSITION_CONTRACTS.md#结论门槛全局强制)

- 来源仍稳定、目标没到、动作明确允许重试时，核对原对象和阻断条件，按已声明的间隔、次数和时限重试。来源已退出时保留原目标，只等待新画面，超时留证。
- 证据缺失或冲突时暂停输入。已识别的覆盖层交给约定的处理方，复验后再接回。未知状态只允许已经证明安全、次数和时间都有上限的恢复。关键安全判据缺失时停止。
- 购买、领取、传送或消耗体力等不可逆动作发出前，要在同一画面确认玩家授权、目标对象、控件可用，以及适用的价格、数量、余额或限额。已经发出但没有明确回执时，停止再次提交，保留现场并对账，确认实际结果后才决定下一步。重启、重复启动、迟到回执和异常收尾都要保留已经发生的业务事实。

## 3. 从现场到交付

先从玩家入口走到真实回执和合法终点，写清会改变下一步的画面、接力点、弹窗归属和断点后怎么处理。给判据配上正例和最接近的反例。修故障先复现旧行为，再改动并验证真实入口确实经过护栏。对受影响的接力入口复验相似误入页，已有进度从可查的业务状态读出。[接力契约](../TRANSITION_CONTRACTS.md#接力契约路线准入的另一半)

**离线回归**覆盖正常路径、连续两轮或重新进入、遮罩与相邻页面、延迟转场或冻结、未知与冲突、资源耗尽或自然终点。提前停止条件逐项回放，核对正向停止证据、最后动作和合法收尾。同一用例实际覆盖多个要求时可以复用。核对危险输入有没有被拦住、迟到的回执会不会重复提交、恢复后数量和终点是否正确。首次引导、冷却、资源不足和回执迟到等异常可以离线验。缺少能复现的依据时，将对应分支标待验。

**实机验证**用当前待验提交，对每个新增或行为受影响的客户端和设置分支，从玩家正常入口实机跑至少一轮。事先取得授权，全程无人补点，核对请求量、实得量、真实回执、资源消耗和合法终点。确实只读的任务核对实际读数。支持桌面每日编排的路线还要有一次正常编排入口记录，证明前后任务能在各自终点交接。单个本地账号、一台机器、当天即可满足验收。保留本次计划的全部尝试，发生一次真实失败就退回。[实机闭环验证](live_verification.md)

**留存证据**时注明运行的起止、核对用的客户端、设置和版本。保留原始画面及脱敏日志，能追到前后状态、尝试次数、等待或拒绝的原因、首个故障和最终结论。记录环境与输入、入场、页面或账号状态、转场、回执、收尾中哪一步出问题。离线、实机、干跑、分段和人工操作照实记录。交付时更新变动的路线规则，把证据缺口写进待办，并核对验证版本与交付版本一致。[待办](../TODO.md) · [填写验收记录](route_acceptance.md)

### 一次启动只有一个结论

一次独立启动只算一次，内部循环多轮也一样。先判是否不安全，再看首个故障。此前无故障且玩家主动取消时记中断。其余按预先约定的提前停止或完整业务闭环判定，证据不足记失败。

| 结果 | 如何判断 |
|---|---|
| 完成 | 正常入口无人代点，目标量或自然终点成立，有真实回执，资源在限额内，确认到达合法终点。计入业务闭环分子与分母。 |
| 预期停止 | 命中事先声明的条件，有正向证据并安全收尾。零工作时能证明已领完、已售罄或次数为零。保留已完成量和剩余缺口，单列。 |
| 失败 | 未知页面、超时、目标未达、部分完成且无声明条件，或收尾失败。保留首个故障和实得量，计入业务闭环分母。 |
| 不安全 | 误点、越权扣费、重复提交或虚报完成。立即暂停该组合的稳定放行。 |
| 中断 | 玩家主动取消且此前无故障，记录时间、原因和当时状态，单列。 |

只读以读到约定值并到达约定终点为完成，和实际业务分别统计。一次启动有多个分支时逐项保留实际事件，最后按首个故障或主要业务目标归类。业务已经完成但退场失败时保留实得量，禁止为补终点重做业务。故障后玩家按下停止键，仍按原故障分类。终点要有正向页面证据确认已脱离局内和浮层。单次点击、动画、计数器自增、程序退出提示和相似的页面外观只能作辅助。[路线终点](../maintenance/route_finish_points.md)

## 4. 返工按故障追踪

按受影响组合、玩家行为和失败原因记录故障。每次补上现场、根因、离线结果、实机结论或待验项。同一判定点第二次复发，先补能区分相似现场的反例。同一种故障第三次修正，停用原有补丁方式，重新核对状态、动作回执、执行方式和职责，再用原现场验证新方案。修复涉及公共原因时，逐个核对实际受影响的路线。

## 5. Agent 体检与评分

先判验收门槛。已确认违规、护栏缺失、当前实机失败或交易待对账时记**阻断**。适用证据还没齐记**待验**。安全、回执、终点、离线回归、正常入口实机和独立复核都符合本页要求才记**通过**。

按组合和待验版本逐项评分。工作区候选单列，写明基线和改动来源。每项适用证据齐全记通过 0 分。缺材料或还没查记缺证 10 分。已见冲突、失败或护栏缺失记不通过 10 分。有明确失败先记不通过。不适用的条件说明已核对的入口或业务边界。共十项，最高 100 分。

| 项目 | 核对内容 |
|---|---|
| 1. 范围与合同 | 六项合同、五项路线声明、设置、接力范围和维护手册相符，证据可追到版本。 |
| 2. 状态与变体 | 关键状态有正例和相似反例或可复现场景，未知能安全停止，覆盖层有处理和接回条件。 |
| 3. 动作前证据 | 正常入口下每处输入能确认来源、对象和阻断条件，遮挡与冲突能拦住输入。 |
| 4. 动作后证据 | 实际执行会验证来源退出、目标稳定或页内新状态。 |
| 5. 等待与恢复 | 未变化、冻结、迟到和超时都有可观察的处理及上限，重试和恢复遵守原护栏。 |
| 6. 资源与授权 | 已验授权、对象、限额和防重复，疑问交易已对账，无资源分支有核对记录。 |
| 7. 业务与终点 | 真实回执计数，保留空态、部分完成和首个故障，有终点及适用的接力、串跑证据。 |
| 8. 离线回归 | 待验版本的用例及结果齐全，修复可复现旧失败，共享改动的调用者已覆盖。 |
| 9. 实机闭环 | 正常入口的授权闭环、各次尝试的边界、目标与实得、用量和终点可核查。 |
| 10. 放行与复核 | 独立评审的结论与证据范围一致，稳定声明只覆盖已验组合。 |

每项记录依据和最小复验条件，汇总列出各组合及最差结论。整改先处理疑似或已确认的误点、越权、重复提交、虚报或待对账，其次是危险动作的护栏和证据缺口，再处理其他阻断或待验。同一优先级先处理跨组合的共同根因，再看分数和影响范围。

## 6. 什么时候可以稳定发布

- **允许启动**由程序入口决定，已放行的既有组合继续在现状页展示。旧验证须按当前版本和设置复核，才可扩大公开支持范围。[当前现状](../STATUS.md)
- **开发通过**需要正常入口的一轮实机闭环和相关离线回放。进入试用时注明已验的客户端、账号状态和未覆盖范围。
- **公开稳定**需要每个新增或行为受影响的组合通过全部适用门槛。领域评审者独立打开原始实机证据与回放结果，核对实际断言、危险动作的同画面确认、回执、终点、资源上限和设置。缺证的组合继续待验或试用。验收记录保留支持声明所依据的证据，现状页列各路线已验和待验项目。[验收记录](route_acceptance.md) · [当前现状](../STATUS.md) · [发布手册](release.md)

发布后可用自愿反馈观察同一组合最近 30 次业务尝试的闭环率，目标至少 95%。手动中断和事先声明的提前停止单列，样本不足 30 次时公布分子、分母和条件。30 次中完成 28 次或更少时，受影响组合退回试用，按失败原因补反例。反馈反映参与者的情况。

发现危险动作或疑似扣费异常，立即暂停受影响设置或客户端的稳定声明并对账。复现原故障、用反例验过修复、重验受影响组合并经独立复核后，才恢复声明。
