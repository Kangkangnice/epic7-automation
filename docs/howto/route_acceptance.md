# 路线稳定版验收

按 **路线 × 后端 × 客户端及版本 × 待发布提交 × 设置分支** 评审。雷电版本、其他模拟器、
STOVE 和 Steam 分别记录。已验证的 Windows、语言、窗口尺寸与输入方式同时写进支持范围。
[现状页](../STATUS.md)的放行是程序入口是否允许启动。[证据矩阵](../SAFETY_MATRIX.md)记录具体做过的验证。

三种说法不要混用：**程序允许启动**指现状页的放行列（代码允许在界面启动该组合）；
**一次实机通过**指开发通过阶段的单轮闭环（一个账号、一个客户端、一次业务结果）；
**公开稳定支持**指公开稳定版阶段，按客户端与账号变体分别留证。前一项成立不代表后一项成立。

## 1. 通过单轮验证后再放行

| 阶段 | 验收 |
| --- | --- |
| 开发通过 | 离线回放和一次已授权的实机闭环。用正常启动入口验证起点、真实业务结果、消耗与终点。 |
| 试用 | 开发通过后注明已验的账号状态、客户端和未覆盖分支。收集不同账号和机器的本地证据。 |
| 公开稳定版 | 每个新增或行为受影响的支持组合独立通过下述门槛，由领域评审者复核记录和实际证据。安全类回归当次阻止放行。 |

已放行的旧路线继续按[现状页](../STATUS.md)呈现。首次按本规范核验前标记为历史放行，
旧的单轮结果可追溯，不能填成已达到多账号稳定版标准。共享识别或输入一旦改动，先对受影响路线跑全量离线
回归，随后优先复验实际使用该能力的高风险路线和本次扩大的组合。旧证据、试用和新版本证据分别保留。

## 2. 开工前写验收合同

每个新建或改动的业务分支，先在验收记录的 `contract` 里回答下表六项，再改实现。
合同描述**玩家看到并会受影响的行为**，不写内部实现；只读、默认、会多花资源的选项分行列出。
优化旧路线时，先列受影响分支和共享能力调用者，再用原入口和现场证据建立能失败的用例。

| 项目 | 必须回答 | 不合格的写法 |
| --- | --- | --- |
| 玩家入口与设置 | 从哪一页、经哪个入口进入；哪些开关开启或关闭；只读分支与付费分支分别是什么 | 「正常进入」「默认设置」 |
| 业务目标与数量 | 本次要做成什么，单位是什么，请求量是多少；固定轮数写请求轮数，自然终点写终止事件 | 「尽量做」「跑完为止」 |
| 资源与上限 | 允许消耗的每种资源及上限；默认关闭的付费项；上限按单次启动计 | 「不花太多」「按需购买」 |
| 业务回执 | 哪一页、哪一行、哪个计数能证明业务已发生；回执被遮挡时怎么办 | 「看到动画」「点完就算」 |
| 合法终点 | 停在哪一页或哪一段链路；是否已脱离局内与浮层；收尾豁免引用哪条登记 | 「回大厅」（不说明从哪一页回） |
| 允许提前停止 | 逐条列出资源耗尽、冷却、次数用完、确实无事可做；每条对应的正向证据 | 「出问题就停」 |

合同的六项同时决定台账字段：入口与设置进 `contract.entry` / `contract.settings`，
目标与单位进 `contract.goal` / `contract.unit`，资源进 `contract.resources`，
回执进 `contract.receipt`，终点进 `contract.terminal`，提前停止进 `contract.early_stop`。
默认终点是稳定回到大厅；[收尾豁免](../../games/epic7/finish_home.py)的路线以该路线可观察的
终点为准，并记录串跑限制。合同与实现不一致时，先判断哪一侧错，再改；不得为了让台账通过而删掉合同项。

## 3. 一次启动只有一个结论

**一次独立启动只产生一个结论。** 正常入口、目标与数量一致、真实回执成立、资源在上限内、
合法终点已确认，且无人代点，才记 `completed`。单独回大厅、点击已发出、退出码 0、计数器自增
都不足以签字。同一进程里的多轮内循环仍只算一次运行。

| 结论 | 成立条件 | 计数口径 |
| --- | --- | --- |
| `completed` | 合同六项全部满足；固定轮数按请求量核对，自然终点按最后一页或其他可证伪事件核对 | 计入业务闭环分子 |
| `expected_stop` | 命中合同预先声明的停止条件；有「确实为空 / 已到上限」的正向证据；安全收尾到合法终点 | 单列，不计入分子与分母 |
| `failed` | 未知页面、超时、未达目标、部分完成但无声明条件、收尾失败 | 计入分母，保留已完成量 |
| `unsafe` | 误点、越权扣费、重复提交、虚报业务完成 | 任一条阻止该组合稳定放行 |
| `interrupted` | 玩家真正主动取消；附停止时间、原因和当时状态；此前没有故障 | 单列，不计入分母 |

判定顺序固定：先判 `unsafe`，再判首个故障，再看是否命中声明条件，最后看业务目标与终点；
都不成立记 `failed`。按这个顺序可以避免同一现场被同时写成两种结论。

### 只读巡检

只读任务以读到约定值为目标，例如支线刷新倒计时、商店已购行、冷却文案。
玩家任务就是读数时，读到约定值并按 `scenario: read_only` 记 `completed`，
这是该只读任务的完成，不是打图闭环。只读运行不得计入打图成功分母或分子；
与打图路线共用入口、同样回大厅，也不改变这一点。`receipt` 写清读到的值和原文。

一次启动可以同时含只读与打图事件，例如先领到免费宠物、再尝试商店购买失败。
分支事件分行记录，**整次启动只取一个最终结论**：按首个故障或主要业务目标归类，
成功步骤不得把这次启动写成成功。打图分支的资源耗尽或冷却才按该分支合同记
`expected_stop`；只读分支读到约定值不借用打图的停止口径。

### 零工作与部分完成

打图分支确实无事可做（奖励已领完、今日次数为零、商品已售罄）按 `expected_stop` 记录，
并给出「确实为空」的正向证据，例如所有奖励行已领取、次数显示为零、商品显示已售。
仅有「没有找到可做的事」不构成正向证据。读数任务读到约定值属于只读目标完成，
不在这里按停止记；口径见上一节。

只完成一部分且未命中声明条件时记 `failed`，保留已完成量、最后动作和来源页。
不得用「已完成的部分也算成功」把它改成 `completed`。命中声明条件但只完成一部分时记
`expected_stop`，同时在台账写明缺口。

### 收尾失败

业务计数成立、但约定终点未确认时记 `failed`，`terminal_verified` 为 `false`，
保留实际完成量。不得为了补终点重做业务，也不得因为「业务已经做完」把结论改成
`completed` 或 `expected_stop`。装备制作 2026-11-17 完成 20 件后连续两次 ESC
仍停在制作页，就是这一类。

### 先故障后人工停止

先发生故障、随后玩家按停止键的，以**首个故障**分类，记 `failed` 或 `unsafe`；
停止时间、停止时页面只作为现场事实附记。只有此前没有故障、玩家主动取消的，
才记 `interrupted`。把故障后的人工停止改填成 `interrupted`，会把失败从分母里删掉。

### 终点判定

合法终点先用正向页面证据确认已脱离局内和浮层，再验约定终点。
快捷菜单四格模板的高分只说明「四格外观在」，不能证明按钮可用：迷宫商人商店帧的
四格匹配分为 0.9053，高于 0.82 阈值，实际是灰的。具体口径见
[路线终点](../maintenance/route_finish_points.md)第一节与第四节。

## 4. 每次验什么

- **正常和账号变体**用发现问题的入口复现。默认设置之外，选择能改变页面或动作的真实账号差异，
  如首次引导、未解锁、赛季页签、免费额度已用、商品冷却或背包接近上限。预先写明哪些应完成，
  哪些应安全停止；路线设置和客户端相同的多轮内循环仍只记一次运行。
- **必做离线回归**包括正常路径 `normal`、连续两轮或重新进入 `repeat`、遮罩或相邻页面 `overlay`、
  延迟转场或冻结画面 `slow_or_frozen`、未知/冲突 `unknown`、资源耗尽或业务终点 `end`。
  每个类别写明具体测试节点和本次提交的执行结果，只写类别名不算回放证据。
  回放依据文件须同时写明完整测试节点（含类名）、待验提交 SHA 和通过结果；
  失败或错误节点不得算通过。已报告的复发故障优先转成真实帧或日志可复现的回归。
- **不可逆动作**须同帧确认意图、正确对象和可用控件，核对适用的资源、数量与价格。近似弹窗、禁用态、
  同行冷却漏识别和迟到回执要逐一证明不会误点或重复扣费。确认已发出而回执缺失时停止并留证，
  按实际结果对账后再决定是否继续，不能直接重跑已提交的交易。
- **完整交接**逐项核对已完成的业务计数、真实回执、终点与耗时。支持每日编排的路线要有一次正常桌面
  每日任务入口记录，证明前后路线都能衔接到各自终点。退出码 0 仍需看真实业务和终点证据，
  退出码 2 仅用于事先声明的正常结束场景。人工中止、跳过、干跑和分段验证单列。
- **失败分类**在 PR 或试用复验中区分环境/输入、入场导航、页面或账号状态、转场等待、业务回执和收尾。
  保留最后动作、来源/目标页和脱敏证据。不公开账号名、余额原图、安装路径或运行目录。

## 5. 量化门槛和记录

稳定版样本需有 **10 次业务闭环，全部通过**，来自 **至少两个真实账号**（各至少 2 次成功）、
**至少两个客户端运行环境**和 **至少 3 天**。计划中须有默认成功、账号变体成功、预期安全停止。
安全停止另计，仍须确认合法的终点。当前提交的同一计划保留全部尝试，全部尝试均为通过才准入；
出现一次真实失败即退回，失败保留在分母中，不得靠另外补足 10 次成功掩盖。
**误点、越权扣费、重复提交、虚假完成均为零容忍项**。

发布后，可用自愿反馈的完整试用台账计算同组合最近 30 次业务尝试的闭环率，目标 **≥95%**。
未满 30 次公开显示分子、分母和条件，标注样本不足。手动停止和预先声明的资源耗尽单列。
低于目标时按下列口径处置：29/30 达标但低于 95% 时维持现状并限期补足样本；
28/30 或更低时退回试用，暂停该组合的稳定声明，按失败机制调查并补反例。
一旦出现危险动作或疑似扣费异常，立即暂停受影响分支的稳定声明并盘点实际入账；
只有原故障已复现、反例已守住修复、受影响组合已重验并经独立复核，才恢复声明。
只影响某个勾选项或某个客户端时，写明暂停范围，不扩大到无关组合。
出现相同失败机制反复报错时，优先复现并修正共享层，报告受影响组合。定期汇总使用本地证据，
反馈样本代表参与试用的人。10 次全过只是放行样本门槛，低频故障仍可能在更大样本上出现。
[Google SRE 的用户旅程与有效事件口径](https://sre.google/workbook/implementing-slos/)。

验收记录在本地准备，账号、环境和运行 ID 用本轮代号。客户端写明确版本与输入通道；
历史只写「版本未记录」的台账可保留归档，不能用于新的公开准入。一条记录代表一次独立启动，
每条运行用 `launch` 标出所属日志与起止时间，供评审人切出这一次启动的边界。
启动边界重叠的记录须人工核对，核对前不贡献独立样本。
台账之外另存每个代号所指的脱敏日志和截图。以下 JSON 演示单条运行，完整验收需填齐合同、
回放与全部运行：

```powershell
$revision = git -C auto_game_unified rev-parse HEAD
python -m auto_game_unified.tools.check_route_acceptance .\acceptance.json --route craft_equipment --backend emulator --client "雷电 9.1.23（Android 9，输入通道=后台）" --revision $revision
```

工具只拒绝它能机器判定的矛盾：证据引用打不开、同一启动换 ID 重报、只读记录填作打图、
请求量与实得矛盾、业务完成而终点未确认、故障后改填人工中止、回放只有类别名、
资源超出声明上限。工具通过时输出「台账通过，待独立复核」，并列出仍需人看的事项。
账号与环境是否确属不同实体、回执画面是否与台账一致、危险动作是否同帧确认、
终点是否真是约定页面、资源上限是否与设置一致，都必须由评审人独立核对。
**工具通过不等于放行。** 未过检查的组合继续试用或修复。

## 6. 为什么加这些门槛

复核 2026-11-12 至 11-19 保留日志，确认了 2 条入场故障、6 条显式转场超时、4 条异常后也无法回大厅，
另有 1 条业务完成后收尾失败。装备制作完成 2 轮、20 件后连按两次 ESC 仍留在制作页；
宠物商店两次有来源页持续存在、四次点击未进入确认框的证据；
另有世界首领战黑屏、社区导航超时和支线相邻场景误转场。
这些是保留日志中的事件计数，包含开发和试跑，缺少版本、跨账号和每条路线的完整尝试分母。

2026-11-20 的复审又确认三类高估：把只读巡检与打图路线共用入口当作打图成功；
把一次启动里的多轮拆成多次运行；把业务已完成、终点未确认记成成功。
同日的工具审计显示，只填类别、代号、结果和终点布尔值的台账仍能通过旧检查，
30 条无原因的人工中止也不会被拦。这些字段本身不能自证，检查器必须回到启动边界和原始日志。
