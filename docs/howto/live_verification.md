# 实机闭环验证

业务目标、接力、合法终点和通过门槛以[路线开发与验收](route_change.md)为准。本文供开发者执行和诊断。实机操作前确认客户端、入口、设置、允许消耗和停止条件。

## 一、先做只读自检

从仓库父目录运行：

```powershell
python -m auto_game_unified.tools.live_check
python -m auto_game_unified.tools.live_check --backend pc
```

自检核对窗口、画面和进程权限，不发送点击。截图正常但游戏没有响应时，优先核对输入通道与权限。游戏和助手一般可使用普通权限；若游戏以管理员权限运行，优先以普通权限重启游戏，或者按当前环境要求对齐助手权限。权限提升是否提示由本机策略决定，以检查结果为准。

若游戏画面已变，但连续诊断帧保持相同，先检查取图是否实时。社区竖屏从 ADB 流直接抓取当前画面，不使用设备临时文件和拼接本地路径的拉取命令。

## 二、执行一次验收

优先从本次要验证的真实入口启动。调试时可以用命令行复现相同业务入口：

```powershell
python -m auto_game_unified.main --mode arena
python -m auto_game_unified.main --mode arena --live --confirm RUN --max-cycles 1 --window-backend pc
python -m auto_game_unified.main --daily --daily-tasks story:2,arena:1 --live --confirm RUN
```

- 第一条是只读干跑。第二条是授权后在 PC 验一局。第三条是授权后在模拟器按指定顺序验编排。
- 可调路线按实际目标设次数，固定次数可省略。刷书签的零次付费刷新仍执行当前货架的扫描与启用的购买。
- `--start-state` 只用于干跑和离线诊断。桌面流程由正常任务入口和设置启动。实机验证桌面交接时，通过桌面选择或其等价入口核对连续任务。
- 用界面「安全停止」或该次运行的停止信号请求停止。资源动作回执未明时保留现场，让有权限的人先核账。

## 三、失败时从哪里查

| 现象 | 优先检查 |
| --- | --- |
| 能截图但点不动 | 客户端与助手权限、焦点与输入通道。用只读自检确认现状。 |
| 日志发生点击，桌面图像却一直没变化 | 确认真实画面、输入反馈与截图是否实时。 |
| 点击后到了另一页，却始终等不到成功 | 核对出手前来源、真实落点和应有回执，保留正例和相似反例。 |
| 结果已发生，无法确认已回到终点 | 保留实际完成量、最后画面与收尾失败证据。已发生的业务先对账。 |

源码运行的过程日志在 `runtime_logs/`，现场帧在 `runtime_diagnostics/`。运行详情按每次启动边界核对。常见退出码为 `0` 完成、`1` 故障、`2` 可解释的资源耗尽、`130` 人工停止；正式验收还须确认真实业务和终点。
