# 失败诊断包与排查流程

适用范围：玩家提交运行失败，维护者接收、定性、修复并回归的完整链路。

诊断包由 `desktop/report.py` 生成，触发点在 `desktop/worker.py` 的收尾阶段。
包内 `investigate.md` 是同一套阅读顺序的随包版本；本文件补充玩家侧操作、
维护侧责任与结论记录格式。

## 一、玩家侧

退出码为 1（运行失败）时，助手在运行产物目录的 `reports/` 下生成压缩包，界面
显示失败卡片。

| 界面元素 | 作用 |
|---|---|
| 短码 | 包名末四位，用于将反馈与压缩包对应 |
| 打开所在文件夹 | 定位压缩包 |
| 复制提交说明 | 复制包名、短码、版本与「现象」一行 |

提交内容为四项：压缩包、短码、失败前的操作、界面最后显示的内容。包内文件
保持原样，不修改、不删减。

退出码 0（达到目标）、2（资源耗尽）、130（手动停止）不生成诊断包。这三类每次
运行都可能出现，留包会使真正的失败难以定位。

## 二、包内结构

| 路径 | 内容 |
|---|---|
| `README.txt` | 提交方式与隐私处理说明 |
| `report.json` | 版本、后端、输入通道、退出码、失败路线、失败动作、Top 分数、日志与画面清单 |
| `investigate.md` | 阅读顺序 |
| `logs/` | 失败路线的日志（本体与一份轮转）、外层进程日志 |
| `frames/` | 失败画面；证据目录（名称见 `report.json` 的 `failure.evidence_dir`）内为 `evidence.json`、`source.png`、`target.png` |
| `config/` | `run.json` 运行条件、`environment.txt` 版本与系统信息 |

体积控制：一包最多三帧；超过 10MB 时整包帧转 JPG，仍超只保留一张。目录内
保留最近 10 份。

隐私处理：用户目录替换为 `%USERPROFILE%`，账号名替换为「账号A」。诊断画面只
包含游戏窗口，不包含桌面或其他程序。

## 三、维护者处理顺序

先取一页结论，再按顺序读包：

```bash
python -m auto_game_unified.tools.triage_report <诊断包路径>
```

工具输出版本、退出码、失败路线、失败动作、分数与阈值对照、画面与日志清单。
完整字段见包内 `report.json`。

1. **定性结束类型。** 只处理退出码 1。0、2、130 属正常结束，不进入修复流程。
2. **确认失败路线与页面。** `failed_route` 为空表示未能从文件名判定，改从
   `config/run.json` 的勾选顺序反推；再看 `frames/` 最新一张，确认停留页面、
   弹窗、黑屏与遮挡。
   - ⚠️ **先核对多张诊断帧是否逐字节相同**（2026-11-24 事故后立）。把包内跨时间点的帧
     比一下 md5：如果完全相同，**先怀疑取图通道返回了同一张旧图**，不要急着定性为
     「页面没变」「按钮点不动」或「网页状态异常」。某次社区签到连续三天的现场帧 md5 全同，
     真实原因是竖屏取图把 `adb pull` 写到了被解析坏的本地路径，程序一直读旧文件；
     日志里的页名和失败原因因此全是对着旧图算出来的。取图路径见 `core/portrait.py`。
3. **读分数。** `top_scores` 是失败帧上各锚点的实际分数与阈值，按分数降序。
   - 分数略低于阈值：判据边缘，检查画质、缩放与比对口径。
   - 分数显著低于阈值：页面不符，或模板已随游戏改版失效。
   - `observed=true` 但页面仍判错：排他性不足，检查同页其他锚点是否被误认。
4. **看时间窗。** 在 `logs/epic7_<路线>.log` 中定位最后一次成功动作到第一个
   失败动作之间的记录，区分「点不动」与「转场未完成」。外层日志的
   `事件=结束` 一行给出退出码、最后输出与现场帧。
5. **查旧账。** 同一坐标或同一页面可能已查过，先检索 `memory/` 与对应路线的
   `docs/maintenance/*.md`；路线里存在刻意的取舍，例如次数用完按正常结束处理。
6. **先写失败测试。** 用失败帧做夹具，确认修改前为红；修改后转绿。反向验证：
   去掉修复能复现故障。
7. **回写。** 在 `memory/YYYY-MM-DD.md` 记录病根、改动与验证结果；缺模板则补
   模板与证据声明；运行受影响路线与全量门禁。

## 四、结论记录格式

```text
短码：
病根：
定性：页面改版 / 模板失效 / 状态机路径 / 时序 / 环境
证据：evidence.json 中 <atom> 分数 <score>，阈值 <threshold>
改动：<文件与动作>
验证：<红测试名> / 反向验证 <复现方式> / 回归 <范围与结果>
```

「定性」一项只能选一类。跨类时以最先触发失败的那一层为准，其余作为加重因素
记录，不并列。

## 五、边界

- 原生崩溃与强制结束只能保留最后一张画面与最后 50 行输出，进程已退出，无法
  再采集。需要更强证据时应引入崩溃转储，成本与收益需单独评估。
- 诊断包不包含桌面、其他窗口与用户输入内容。
- 失败帧与日志来自同一时刻：失败帧复制自 `current.png`，而它每次采集都覆盖。
  证据目录取该路线最新一份，`report.json` 的 `failure.evidence_dir` 记录其名称。
