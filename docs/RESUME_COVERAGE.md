# 开局接力覆盖面

本文回答一个问题：**每条路线的每一个环节，是不是都能「停在那儿就从那儿接着跑」？**

截至 2026-09-18 的实测答案是**还没有**：做到了 5 / 7 条路线、27 / 45 个可停靠环节。

（2026-09-18 修正：英雄合成的 10 个状态里有 2 个是**等待状态**、不是画面，原先按 10 计入环节数是错的，分母由 47 改为 45。）

审计方式（只读，不点击不截图）：逐条路线枚举状态枚举 → 用真的 `detect_resume_point` 跑该路线**每一张夹具**（含 navigation 夹具）→ 再全库跑 `battle_scene_visible` 交叉核对。脚本与输出在 `runtime_logs/_audit_resume.py` / `_audit_out.txt`、`_audit_shop_resume.py` / `_audit_shop_resume_out.txt`（刷书签判据全库负例扫描）、`_audit_hero_anchors.py` / `_audit_hero_anchors_out.txt`（英雄合成逐帧锚点覆盖）（本机产物，不入库）。

## 先分清两件事

| | 含义 | 现状 |
| --- | --- | --- |
| **运行中能不能处理这个页面** | 循环跑到这一页时，状态机的 `next_action` 认识它、知道点哪 | 各路线基本都做了 |
| **开局能不能从这个页面接力** | 你人工把游戏停在这一页，然后启动助手，它从那一步接着跑 | **只有 5 条路线做了** |

这两件事很容易混，用户看到的症状也可能来自后者。典型例子：竞技场的**免费刷新确认页**和**友情券赠送页** —— 运行中状态机都会正确处理，但你把游戏停在那一页再启动助手，它不认识，会一路受控返回大厅从头重走。

## 覆盖矩阵

一个格子 = 一个可停靠环节。实心 = 能接力。

| 路线 | 环节数 | 能接力 | 缺口 |
| --- | --- | --- | --- |
| 主线 story | 8 | **8（全通）** | 无 |
| 远征 expedition | 12 | **12（全通）** | 无 |
| 竞技场 arena | 6 | **6（全通）** | 无 |
| 刷书签 shop_refresh | 10 个内部阶段（1 张可停靠页面） | **1（全通）** | 无 |
| 狗粮 fodder | 6 | 0 | 全部 |
| 英雄合成 hero_synthesis | 8（另外 2 个状态是等待状态，不是画面） | 0 | 全部 |
| 活动挂机 survivor | 4 | 0 | 全部 |

夹具层面「认得出」的比例：主线 27/33、竞技场 15/18、远征 16/16、刷书签 15/22（商店页本体，
另有 4 张弹窗刻意不接力）；其余三条路线一张都不接力。
主线那 6 张不认的全部是弹窗（2 张体力弹窗、好友请求、亲密度弹窗、战斗指南弹窗）或一张 2026-08-19 的旧桌面截图 `battle_variant.png`（不是有效夹具），**不是页面级缺口**。

## 逐路线明细

### 主线 story — 8 / 8 全通

关卡入口（`story_ready` / `prepare_battle` / `watch_story`）、队伍准备（`start_mission`）、助手选择（`select_team`）、跳过确认（`skip_confirm`）、剧情播放（`skip`）、战斗中（`battle_scene_visible`）、结算类（`results_confirm` / `clear` / `reward`）、通关提示与额外奖励与下一关入口（`complete` / `bonus_reward` / `next_stage`）全部能接力。局内接力不按 `Back`，直接交战斗监督等结算。

### 远征 expedition — 12 / 12 全通

远征主页、通缉传单列表、难度选择、难度确认、准备战斗（营火）、队伍选择、战斗中、战斗结果、公开招募结果、招募确认、招募后返回、返回主页。
另外导航链上的**战斗菜单 / 赛季菜单 / 远征主页**三级都能接力（`entry` 落点，跳过它之前的转场）。

### 竞技场 arena — 6 / 6 全通

能接力：竞技场模式选择（额外入口）、对手列表、对手详情、队伍选择、战斗结果页、结果确认中、战斗中。

一轮六个环节（列表 → 详情 → 队伍 → 战斗 → 结果 → 确认中）**全部接得住**，外加「模式选择」这个额外入口。
判定顺序：模式选择（靠 `observed_page`）→ 对手详情 → 队伍选择 → 对手列表 → 战斗结果页 → 结果确认中 → 战斗中。

**2026-09-16 补齐了最后两步**，两个坑都是「判据」问题、不是「锚点」问题：

| 补的是 | 当年的障碍 | 怎么解决 |
| --- | --- | --- |
| **战斗结果页** | 识别它的 `confirm` 锚点**与远征结果页共用** —— 实测远征 `result.png` 上这个锚点拿 0.9448，高过 0.90 阈值。没有排他证据就接力，会把远征的结算当竞技场的接着跑 | 从 `epic7_arena/result.png` 裁了两个竞技场专有内容锚点：`result_rating`（「积分」面板标题，**胜负都会出现**，做主判据）与 `result_victory`（「VICTORY」横幅，只有赢才有，做冗余）。在 `arena.result_arena` 页里与 `confirm` 组成合取判据，阈值 0.80 —— 全仓库 196 张夹具里除那张结果页外，`result_rating` 最高 0.3460、`result_victory` 最高 0.2724，离 0.80 还有一倍距离 |
| **结果确认中** | 状态机的 `_STATE_TEMPLATE` 里没有这一状态的锚点 | 它其实就是段位提升弹窗，`find_rank_promotion_confirm`（绿箭头 + 确认按钮 HSV 双锚点）早就认得出（实测 0.9993 / 1.0000），只是此前没接进接力链 |

两个「运行中会处理、停在那一页不接力」的弹窗：**免费刷新确认页**、**友情券赠送页**。它们是弹窗而不是环节，不列入环节数，也不打算接力。

另有两条不放进环节数、但已经接住/显式排除的画面：
- **买票弹窗压住的队伍页**：`battle_start` 在弹窗下仍然可见（0.9996），会被误判成队伍页，接力过去直接点到购买按钮上，故用 `no_ticket` 显式排除。
- **局内**不在状态机里认（4 张局内实时帧只有 1 张能靠 `auto_off` 认出来），改由 `detect_resume_point` 用 `battle_scene_visible` 兜住。

### 狗粮 fodder — 0 / 6

关卡地图、准备战斗、队伍选择、战斗中、结算、重新进行，一个都没有。

- **好消息**：锚点已经全齐 —— `navigation/fodder_stage_title`（关卡地图）、`fodder/prepare_battle`（准备战斗）、`fodder/select_team`（队伍选择）、`fodder/clear` 与 `fodder/results_confirm`（结算）、`fodder/replay`（重新进行），加上 `battle_scene_visible`（局内）。属于「只差接线」。
- ⚠️ **坏消息（做之前必须先解决）**：`fodder/replay.png`（「8/36 + 重新进行」那一页，带暂停键和左侧队伍血条栏）会被 `battle_scene_visible` **误判成局内**（实测返回 `True`）。如果照搬主线/远征「先判局内」的顺序，停在结算页启动会被当成已承诺战斗去监督，而不是点「重新进行」。要么给「结算 / 重新进行」锚点更高优先级，要么收紧 `battle_scene_visible`。
  已核实：目前三条路线**没有**这个问题，挨个验过它们的全部非战斗页，零误命中。

### 英雄合成 hero_synthesis — 0 / 8

它声明了 10 个状态，但**其中 2 个不是可停靠画面**（原先把它们也数成环节，分母虚高了 2）：

| 状态 | 是什么 | 能不能接力 |
| --- | --- | --- |
| `IMPRINT_ABORTING` 中止刻印等待返回 | 纯等待状态（等返回动画走完） | 不是页面，不需要素材 |
| `TRANSMIT_RETURNING` 传送后返回列表 | 纯等待状态 | 不是页面，不需要素材 |

剩下 8 个是**画面**，全部**零接力**。缺的不是「路线跑得动需要的锚点」，而是**排他**锚点：

| 画面 | 现有锚点 | 缺什么 |
| --- | --- | --- |
| 英雄列表 | `filter_button` ✅（PC 端这张过不了阈，见下） | PC 端锚点 |
| 筛选面板 | `filter_level_label` / `filter_star3_selected` / `filter_star3_unselected` / `filter_attribute_label` ✅ | 无 |
| 刻印加材料 | **只有通用的 `story_back` 返回箭头**（实测 `imprint_added` / `imprint_up_cards` / `imprint_up_one_card` 三张都只命中它；`sss_material` 是「有 SSS 材料」的提示，不是页面判据） | 页内专属锚点 |
| 合成确认（弹窗） | **只有 `story_back`**（实测 `synth_confirm.png`） | 弹窗专属锚点 |
| 合成结果 | `imprint_result_title` + `imprint_result_close` ✅ | 无 |
| 传送选择 | `auto_select_label` ⚠️ **不排他** | 与下面两页区分的锚点 |
| 传送确认（弹窗） | `auto_select_label`（实测 `transmit_confirm.png` 上 1.000）⚠️ | 弹窗专属锚点 |
| 传送奖励 | `transmit_reward_title` + `transmit_reward_close` ✅ | 无（`auto_select_label` 在这页同样可见，是下面那条「不排他」的问题） |

实测方式：`runtime_logs/_audit_hero_anchors.py`（只读）拿现有 hero 证据档跑全部 24 + 14 + 2 张 hero 夹具，
逐帧列出过阈的原子；**34 张能命中至少一个原子，6 张一个都命中不了**。

⚠️ **`TRANSMIT_SELECT` 其实是有锚点的**（`auto_select_label`），早先文档写「没有对应模板」是错的。
真正的问题更麻烦：**这个锚点在「传送选择 / 传送确认 / 传送奖励」三页上都可见**（实测都是 1.000），
单靠它分不出是哪一页 —— 而把「传送确认」弹窗误认成「传送选择」会**重复点一次不可逆的传送确认**。
所以这一支要的是**排他**锚点（弹窗标题那类），不是「再补一个模板」。

PC 端另有一层缺口：`epic7_pc_hero/` 里 `07_imprint_materials`、`09_imprint_all_materials`、
`10_synthesis_confirm`、`13_imprint_result_closed` 四张**一个原子都命中不了**，另外几张只命中
`imprint_normal`（0.85~0.88）与 `filter_level_label`（0.73），`filter_button` 在 PC 英雄列表上过不了阈。
即使补好接力逻辑，PC 英雄列表也需要单独采锚点。

**为什么「按顺序明明能走通」**：运行期是**状态驱动**的 —— 每一页都是从上一个已知状态点进去的，
认页面只在两处需要，而这两处都有别的手段：

1. **弹窗靠形状 + 状态上下文**：合成确认与传送确认共用同一套「蓝色确认按钮带 + 金色内容带」形状检测
   （`_confirm_button`），靠 `_locate("auto_select_label")` 在不在、或者 `state` 是不是 `transmit*`
   来分是谁（`hero_synthesis.py:1382-1415`）。
2. **传送奖励层只在传送流程中才判**（`transmit_phase is CONFIRMING` 或 `state` 是 `transmit*`，
   `hero_synthesis.py:1417-1421`，注释写着「防止列表误触」）。

接力没有这个上下文：**开局只有一帧**，必须从像素反推「我在哪一页」，所以需要排他锚点。
这两件事不矛盾，也别互相当成「已经做完了」。

### 刷书签 shop_refresh — 1 / 1 全通（2026-09-18 补齐）

它的 10 个 phase（`SCAN_TOP` / `WAIT_SCROLL_RESULT` / `SCAN_BOTTOM` / `WAIT_PURCHASE_CONFIRM` / … / `COMPLETE` / `STOPPED`）**不是 10 个页面** —— 整轮都待在同一张秘密商店页上，这些是内部阶段，不是可停靠画面。

所以对它来说「接力」= 认出「已经在秘密商店页」→ 直接开始扫描。

| 要点 | 做法 |
| --- | --- |
| **判据** | 与导航器的「秘密商店」页面识别**同源**：都调 `ShopRefreshObserver`，都要求「商店标题 + 立即更新(3 空窗) + 购买按钮」三个锚点同时过阈。不新定阈值、不加新锚点 |
| **拨不拨状态** | **不拨**。phase 没法从中间接，起始恒为 `SCAN_TOP`；探针只给状态机打 `mark_resumed_at_shop()` 记号 |
| **接力准备** | Runner 见记号先做一次「列表回到顶部」的滑动再开扫。人停下时列表可能停在半截，直接当「顶部批次」扫会让 `_scroll_to_bottom` 滚不动，整轮以「滚动到底部结果不明确」失败 |
| **弹窗** | 刷新确认页 / 购买确认页**刻意不接力**：`return_home` 的那一下 Back 会先关掉弹窗，下一帧扫到商店页就地接管，没必要为弹窗单独建判据 |
| **负例扫描** | 全库 197 张夹具跑判据（`runtime_logs/_audit_shop_resume.py`）：176 张可判，其中 `shop` 15 张**全部**是秘密商店页本体、`purchase_confirm` 3 张 + `refresh_confirm` 1 张都是商店自己的弹窗，**其余 157 张全是 unknown，零跨路线误命中**（另有 21 张 3200×2000 的旧夹具被匹配层按宽高比拒绝，失败关闭） |

### 活动挂机 survivor — 0 / 4

首卡页、局内、升级三选一、结算，一个都没有。

- **特殊**：它的 4 个状态**锚点其实都齐**（`weapon_card_label` / `battle_score_label` / `level_up_title` / `result_title`），卡点在它 `needs_navigation=False` —— 本来就是人工把游戏推到活动里再启动，而接力机制挂在 `return_home` 的钩子上，所以没接上。
- 它要改的是**启动时认画面决定起始状态**，而不是硬编码「首卡页」。

## 建议的补齐顺序

按「离做完有多近」排：

1. **狗粮** —— 锚点齐全，只差接线；但必须先解决 `replay` 页被误判成局内的坑。
2. **活动挂机** —— 锚点齐全，改入口的状态判定逻辑。
3. **英雄合成** —— 不缺「顺序跑得动」的锚点，缺的是**排他**锚点：合成确认 / 刻印加材料要采弹窗与页内锚点，
   传送那一支要能把「选择 / 确认 / 奖励」三页分开；PC 端还要另外补英雄列表锚点。最慢。

## 维护约定

- 补一条路线的接力时，**顺手 grep 其它测试里把它当「反例样本」用的地方** —— 2026-09-17 给远征补探针时，就有 4 条既有断言因为把 `expedition` 写在「探针必须为 None」的名单里而失败。
- 同理，**把某个页面从「不接力」改成「接力」时，先 grep 断言它必须为 None 的测试** —— 2026-09-16 补竞技场结果页时，`test_arena_resume.py::test_result_page_is_not_a_resume_point` 就是这种「反向断言」；2026-09-18 补刷书签时，三个文件里各有一处 `for name in ("fodder", "hero_synthesis", "shop_refresh", "survivor")` + `assertIsNone(get_mode(name).resume_probe)` 一起挂了，都要把 `shop_refresh` 从名单里去掉。
- 新路线的接力点顺序表要**自带注释写清为什么这么排**，顺序即优先级。
- **跑得通不代表认得出**：接力判据的验收标准是「拿真夹具跑真 `detect_resume_point`」，不是「测试全绿」。补完一步后，除了单测，还要跑一遍该路线的全夹具计数脚本（如 `runtime_logs/_audit_arena_count.py`）确认命中数确实涨了、且没有跨路线误命中。
- **一条正例不够**：新锚点必须有**跨路线负例扫描**（全库夹具取最高分）才能定阈值。竞技场这两个锚点就是靠全库 196 张的最高分 0.3460 / 0.2724 才敢用 0.80 这个比默认松的阈值。
- 改动后跑针对性门槛：`compileall` + 该路线的 `test_*_resume.py`；动了 `navigation.py` / `main.py` / `modes.py` 才需要跑全量。
